## 结论

**1. 范围一级的事实写在范围自己的对象上。**ServingGroup 是 CR，名字不带序号。「这个组要整组替换」是它 `status` 上的一次写；「这个 Role 实例建成过」「正在清空」是它 `status` 里一张小表（账本）上的一项。今天这些事实在内存里，或者拆开写在每个 Pod 上。

**2. 组一级是 Deployment 的滚动算式加按数量的 partition。**没有 surge 的标记、转正和回收，没有序号空洞。还有过期的组时上限是 N + S，否则是 N；最后一个过期的组删掉时数量正好是 N。

**3. 状态不存储，每一轮从对象判定；每个状态的动作只取决于这个状态。**所以换主、重启、被接管之后做的事相同。把每一次写当作一个可能停下的点逐行列过，没有「取决于原进程记得什么」的格子。前提是：选主打开、失主退出、新进程过了接管屏障才开始写。

**4. 行为大部分没有变。**契约 2.12 的 35 个组合场景在本设计的规则上重放：31 段脚本的可观察量与契约相同，11 段不同，都是有意的。其中 6 处是每次带 S 的滚动少建少删一个组，3 处是少一两次重建，1 处是百分比 partition 在扩容之后多留一个旧版本的组，1 处终态变差（一直起不来的新版本的组不再被当成临时 surge 回收）。用例目录的 1013 项里 148 项是有意变化，2 项留给真实验证。

**5. 有 13 条契约条款在字面上被碰到，要逐条批准。**最重的三条：账本是一张逐实例的表（契约 2.9 明确不要）；controller 不在时发生的丢失回来之后按范围恢复（契约是只补）；组一级的 partition 按数量（契约是绝对序号）。

**6. 已运行的负载可以不断服地升级，但新旧进程一刻都不能重叠。**接管只改元数据，存量的组保留原来的名字。旧进程看到 Pod 的 owner 被换掉，不是报错，是删 Pod；所以独占要由新版本自己保证。回退是新版本的一个受控模式，不是 `helm rollback`。

**7. 两处已知的局限。**健康额度按晚一跳的 `status` 算，一个组刚失去就绪的那一小段时间里滚动可能多删一个健康的组。两个进程并存时可能多建组，事后缩回。

## 要裁定的

### 沿用 007 的推荐

| 007 的编号 | 内容 | 本设计 |
| --- | --- | --- |
| K5、T10 | 粒度 | 只有 ServingGroup 是 CR。Role 实例保留序号 |
| K1、T11 | 组怎样被删 | 前台级联；等故障成员清空再删 |
| K2、T12 | 组一级的 partition | 按数量 |
| K4、T13 | 多建 | 接受事后缩回。范围收窄到两个进程并存时 |
| T14 | 实例建成之前的丢失 | 只补 |
| K6、T16 | 失败的组消失之前先建替换的 | 不做 |

### 碰到的契约和已批准的决定

- 契约 2.12 的 13 条：[04](04-behavior-expectations.md) 第 11 节的 C1 到 C13。**批准之前不改 runner 的文档和用例。**
- D1（surge 被 N 覆盖时转正）在组一级不再适用。D12 的后一半变了（04 的 C10）。D11 的例外从「已经开始」扩大到「已经提交」（04 的 C12）。
- 007 的 05 里原地更新的限制（T17–T21、T26）不因本设计改变，仍然等裁定。

## 没有做的和没有验证的

- 没有改 controller 代码、现有测试、CRD、chart、runner 的契约和用例。因此没有做 Kind 验证，任务状态保持进行中。
- 没有修改 005、007 的文档。
- 模型检查的是规则，不是实现。组一级的模型最多 3 个组、3 个版本；账本的模型是一个实例两个成员。两个模型没有合成一个。
- Role 一级的规则沿用 v2，没有重新分析；它和账本的衔接是推演。原地更新没有模型。
- 用例目录里逐例推演过的只有 35 个组合场景、RC-01 到 RC-04 和十几个点名的用例，其余按规则归类。
- 关于旧版本行为的结论（owner 被换掉之后它删什么）来自读代码，没有运行过。
- 关于 Kubernetes 行为的结论（前台级联、垃圾回收器对 owner 的处理、一致性的 LIST、Helm 对 `crds/` 的处理、PDB 对 `scale` 的使用）按文档和源码，没有在集群上验证。
- 没有做过任何一次升级演练。
