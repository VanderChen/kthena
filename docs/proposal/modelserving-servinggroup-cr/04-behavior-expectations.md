## 2. 怎样从差异点推出其余场景

上一版的组一级规则与契约不同，其余场景靠「依赖哪个差异维度」推出来。这一版组一级的规则与契约是同一套，场景直接重放比对，不再靠推。

| 场景属于 | 怎样得出结论 | 证据 |
| --- | --- | --- |
| API 校验、拒绝 | 准入规则不在本设计的范围内。一致 | — |

## 5. 恢复：策略 × 触发

已建成的 Role 实例（账本是 Established）。规则在 02 的 5.3。

| 触发 | `None` | `RoleRecreate` | `ServingGroupRecreate` |
| --- | --- | --- | --- |
| 成员被删除（controller 在场） | 补这一个 | 重建这个实例 | 整组恢复 |
| 成员被删除（controller 不在） | 补这一个 | **重建这个实例**（契约的字面：只补；见表下第一条） | **整组恢复**（契约的字面：只补；见表下第一条） |
| 成员是 `Failed`、`Succeeded` | 删这一个再补（D10、D13） | 重建这个实例，不等 grace（D13） | 整组恢复，不等 grace |
| 重启故障，grace ≥ 0 | 只报告 | 满 grace 之后重建这个实例 | 满 grace 之后整组恢复 |
| 重启故障，grace 是 `-1` | 只报告 | 只报告 | 只报告 |
| 未就绪，没有重启 | 等待 | 等待 | 等待 |
| 整个组的 Pod 都没了（只在 `ServingGroupRollingUpdate` 下） | 整组恢复 | 整组恢复 | 整组恢复 |

- **「controller 不在」分两种**（用户 2026-11-23 的口径）。升级 controller、主备切换、多副本时主被删或者主所在的节点故障，算在正常运行的容灾范围里，不赦免：这期间丢了 Pod，照 `recoveryPolicy` 的范围处理。赦免的是 controller 完全故障，和 controller 被删除之后发生的变化：这两种允许只补。这一版对两种不作区分，都按范围恢复：账本在对象上，从对象上看不出 controller 离开了多久、为什么。所以不赦免的各种情形下这一版符合口径，今天的两个版本在这些窗口里都只补；赦免的两种情形下照范围恢复也可以，用户已确认（第 11 节的 C2）。
- **最后一行先于上面各行。**条件是：组期望有成员，账本里有建成过的实例，一个成员 Pod 都没有了（属于这个组的、待接管的、终止中的都没有），并且直读确认过。ServingGroup controller 写 Failed，Drained 同时为真，不再创建。每组只有一个 Pod 时，这个 Pod 每丢一次，组对象换一个；PodGroup、headless Service 跟着重建，`None` 下也是这样。整个组的 Pod 是逐个丢的时，走不走这一行取决于有没有一轮正好看到一个都没有：看到了按序号和 partition 重建，没看到就逐个按组的版本补。`RoleRollingUpdate` 下没有这一行：版本按 Role 的 partition 选，ServingGroup controller 自己有，照上面各行处理。
- **策略和 grace 取动手那一刻的。**要写 Failed、写 Draining 的轮次直读所属的 ModelServing（02 的 5.3）。它是动手之前的最后一道，所以分方向：改成 `None`、`-1`、更长的 grace，和范围的改变，在动手那一刻生效，不用等下发到每个组，升级接管没做完时也生效。打开策略（从 `None`、`-1` 改成别的）、缩短 grace 要等下发到组；接管没做完时不生效。
- controller 不在时的丢失有一个例外：从旧版本升级上来的第一次，账本从零值开始，升级的空窗里丢的只补（[06](06-live-upgrade.md)）。**这一次不符合上面的口径**（升级不赦免）。它与今天旧版本自己升级时相同，不是回归：旧版本没有把「建成过」写在任何对象上，接管时分不出「没建完」和「丢了」。用户已接受这个缺口（2026-11-23）。已建成的实例里正在终止的成员也算丢失。
- 创建中的 Role 实例（还没有写上 Established）：成员**被删除**一律只补，三种策略相同。成员是 **`Failed`**（以及上表里别的故障）仍然按上表的范围恢复（03 的 4.3 的 E5）。两者在实例建成之前的结果因此不同：API 驱逐是删除，只补；节点压力驱逐留下的是 `Failed` 的 Pod，按范围恢复。对被删除的成员，契约在连续运行时按范围恢复；在网版本连续运行时已经是只补。

**整组恢复**（02 的 5.4）。写 Failed 是提交点，写之前直读确认。之后：ServingGroup controller 只删故障的成员，其余成员继续运行（D15）；没有故障成员、没有正在终止的 Pod 时写 Drained；ModelServing controller 前台级联删除这个组；组对象在 Pod 都消失之前一直占着它的序号；对象消失之后，G4 在小于 N 的最低空闲序号上重建。连续的序号集合下就是原来的序号：组名、Pod 名都不变，UID 是新的。稀疏布局下范围内的组可能落到更低的洞上（第 11 节的字面出入）。失败的组带 surge 标记时，它消失之后要不要在那个序号上再建一个 surge，按当时有没有滚动要做决定。

**重启故障的起点**（02 的 5.3）。在 ServingGroup controller 的内存里，与今天相同（D9）：第一次看到一个成员未就绪并且有计划外的重启时记下时刻，满了 grace 按上表处理。成员恢复过再坏、Pod 换了，重新计。改 grace 不动起点，到期按当时生效的 grace 现算（副本和缓存里的 ModelServing 两者中较长的一个）。换主、重启之后新的进程重新计满一个 grace，离线的时间不计。`None`、`-1` 不计时；改回有限的 grace 之后从 controller 下一次看到故障的时刻起算。与契约 API 参考 6.2 相同。

起点只决定提交什么时候发生。范围已经提交时（组是 Failed，或者实例在清空），在重启故障里的成员直接算故障，不看 grace：提交之后换了进程，新进程照样先删故障的成员，其余成员继续运行（D15）。计时的时候恢复生不生效取组里的副本和缓存里的 ModelServing 两者中保守的一个：策略还没下发到组时把 grace 改成 `-1` 再改回来，改回来之后重新计满一个 grace。计划内清空一个实例时（Role 缩容、Role 一级的滚动），里面在重启故障里的成员同样先删，多等它的一个终止期。这几条是推演，没有模型。

用户的口径（2026-11-23）：grace 的计时可以赦免，因为它只影响时间；按范围的恢复直接影响 Pod 的生命周期，才必须在升级和主备切换的窗口里成立（第 11 节的 C2）。

## 9. plugin 调用点

框架的四个钩子按调用点的变化分析，在 [02](02-design.md) 第 7 节。特定实现的 plugin 不分析。相对上一版变了两处，其余不变：

| 项 | 这一版 |
| --- | --- |
| `HookRequest.ServingGroup` | 是组名，格式与今天相同，仍然可以从里面取序号。上一版在随机名字下取不到 |
| `HookRequest` 带的身份 | 另带组的 UID 和实例的代际号。代际号只在一个组的 UID 之内有意义：同名重建之后新对象的账本从零值开始，代际号又从头数。内置的 headless Service plugin 靠进程内的记忆防止把旧的删除决定用到新对象上，要改成对象上的事实：Service 创建时写上组的 UID 和实例的代际号，删除之前比对 |

对 `plugin-retry` 套件的 4 例，结论仍是有意变化（推演）：

| 用例考的 | 变化 |
| --- | --- |
| `OnPodCreate`、`OnRoleSync` 失败之后重试 | 调用者换了，重试的方式不变（这一轮出错，下一轮再来） |
| `OnRoleDelete` 失败 | 今天在 Pod 的 DELETE 发出之后调，失败不挡删除。这里实例被清空时在删 Pod 之前调：调之前直读复核账本仍是 Draining；失败则这一轮不删，下一轮重试；一直失败时实例停在清空中，挡住恢复、Role 缩容和按重建的 Role 滚动，组上报 `DrainBlocked`。整组删除时只尽力调一次，失败不重试 |
| SG 模式的 RUN-536、537 | `ServingGroupRollingUpdate` 下滚动、缩容、整组恢复全是整组删除，`OnRoleDelete` 在这个模式下从来不保证调到。用例注入「连续失败 2 次再恢复」之后不会再有重试；期望里的「不泄漏旧的和多出来的资源」要靠 plugin 的资源挂在 ServingGroup 名下、由垃圾回收清掉 |

### 10.2 直读重算和复核

规则在 02 的 6.3。这一版没有在途登记、在途屏障、启动时的一致性 LIST 和接管屏障：新进程里两个 controller 之间没有先后的要求。

| --- | --- | --- |
| 新进程的第一次 LIST 是旧的；那之后一个组变成未就绪，原进程已经删了它 | 有写要发的轮次先直读：那个组在终止中，健康额度是 0，不删 | 按缓存里「三个都就绪」删掉另一个健康的组 |

| 刚转正了一个组，缓存还没看到；N 又调小 | 直读里它是正式的组：先缩容 | 把它当 surge，先替换了别的组 |
| 缓存里一个组是未就绪，实际已经恢复就绪；或者旧进程里它还带 surge 标记，实际已经转正 | 组的 DELETE 带 UID 和 resourceVersion：组在观察之后有任何变化，这次删除不成立，重新计划 | 健康的组被当成未就绪的旧组、或者当成 surge 删掉 |

| 一个组刚丢了成员，`status` 还没写成未就绪；同时来了新模板 | 这个组的 Pod 少了一个，`status` 不新鲜，不算确认就绪：健康额度里没有它 | 按 `status` 里的 Ready 多删一个健康的组 |

| controller 停着的时候一个组的 Pod 恢复了，`status` 还写着未就绪；新进程起来 | `status` 不新鲜，按未观测算：不当成未就绪的旧组删掉 | 按停机之前的未就绪删掉它 |
| `spec` 刚下发时提交新版本（EX-3） | 未观测的组不被替换 | 把未观测当成未就绪去删 |
| `spec` 刚下发时缩容；一个组刚变坏、`status` 还没写出来时缩容 | 次序看 Pod 缓存：没有 Pod、有 Pod 不就绪或者在终止的组先删 | 删了健康的组，留下坏的组 |

### 10.3 同名重建

规则在 02 的 4.5、5.5。

| 场景 | 预期 | 必须判错的 |
| --- | --- | --- |
| 滚动替换、整组恢复 | 旧对象在名下的 Pod、PodGroup、Service 都消失之前一直在，一直占着序号和一个位置。之后才建同名的新对象：UID 不同，账本是零值 | 旧 Pod 还在时新对象已经建出来；新对象沿用了旧的账本；对旧 UID 的写落在新对象上 |
| 一个组卡在终止中（有人加了 finalizer；垃圾回收器停了） | 它的序号不能重建，不绕过去另建。报 `WaitingForDeletion`，message 写明序号。它是正式的组时，N 调小之后还会挡住滚动。带 S 的滚动照常做完，surge 回收之后，U ≥ 1 时一直少一个，直到它消失。上一版在带 S 的滚动途中可以换一个名字补建，这一版不能；与今天一个 Pod 卡在终止中相同 | 报成别的原因；换一个序号补建 |

| 用户用前台方式删一个组 | 与缩容、替换的删除相同 | — |
| 用户用 orphan 方式删一个组：留下无主的成员 Pod | **找回**：ModelServing controller 给这个序号重建对象。版本取这些 Pod 的 revision 标签；不一致或者对应的 ControllerRevision 不在时按序号和 partition。`ServingGroupRollingUpdate` 下序号不小于 N、并且至少一个 Pod 带组一级标记的副本时，建出来的对象带标记。**收养**：ServingGroup controller 换 owner，Pod 的 UID 不变。收养来的成员版本与组的不同时，组报 `RecreateRequired`，在预算之内替换。多出来的组按缩容处理。找回的对象在它的 Pod 被收养完之前不是缩容、回收、替换的候选，只占位置（02 的 5.5） | 无主的 Pod 被删，或者长期没人管；surge 的组找回来成了正式的组 |
| 稀疏的序号集合（`{1, 3}`、N = 2），orphan 删 `sg-3`；组的缓存先显示少了一个组，Pod 的缓存还没显示无主 | 先在序号 0 上多建一个组，随后找回 `sg-3`；正式的组 3 个，缩掉一个，未就绪的先。这是写明的分不清的情形。连续的集合下不会这样 | 删掉两个；留下的不足 N 个 |
| 名字对不上任何期望成员、或者不带代际号标签的带标签 Pod（`kubectl debug --copy-to --keep-labels` 的副本是前一种） | 不是无主的成员 Pod：不为它找回，不让它所在的组变成待收养，不收养，不删除，发事件报告 | 被删；被算进组的计数；为它多建一个组；它所在的组一直不能被缩容、替换 |
| 序号上有无主的成员 Pod，同时被外来的同名对象占着 | 不找回，报 `OrdinalOccupied` | 静默地没人管 |
| 待收养的组一直收养不完（换 owner 一直被拒绝） | 超过期限报 `GroupNotObserved`，message 写明哪些 Pod | 一直不报 |

### 10.5 恢复和没有成员的组

| 场景 | 预期 | 必须判错的 |
| --- | --- | --- |
| 整组恢复（NEW-1） | 组写上失败；故障成员消失之前其余成员继续运行；之后组被删；Pod 都消失之后才在原序号上重建，名字不变，UID 是新的 | 故障成员还没停就删其余成员；失败的组还在时就建了替换的 |
| 灰度停点上一个组失败（NEW-2、NEW-3）；灰度还没滚完时受保护的组失败（NEW-7） | 重建的组的版本按它的序号和当时的 partition：序号小于 P 用基线，否则用目标 | 用错版本 |
| 滚动中一个旧组失败（NEW-5） | 失败的组被删；预算照算 | Ready 被替换拉到 `minAvailable` 以下 |
| 整个组的 Pod 都没了（`ServingGroupRollingUpdate`） | 组写 Failed，对象被删，在这个序号上按序号和 partition 重建。任何恢复策略下都这样 | 按组原来的版本补；ServingGroup controller 自己按旧版本重建 |
| 各 Role 的副本数都是 0 时提交新版本，再调回来（NEW-6、NEW-9、NEW-10） | 没有成员的组按它的序号重新指派版本，只改 `spec.revision`，不占预算。范围外的空的正式组在低位现在就建得出来时删掉。空组算就绪，有空组时基线不推进。调回来时各组按自己的版本建 Pod | 有 Pod 的组被改了版本；调回来时先按旧版本建 Pod 再被替换；低位补不上还删了范围外的空组 |
| 对象建了、Pod 还没建出来时提交新模板 | 还没有开始建 Pod 的组（刚建出来的对象；PodGroup 建不出来而卡住的）：`spec.revision` 改成按序号现在新建会用的版本，放开之后按新版本起。已经开始建 Pod 的（Pod 的创建被拒绝）：它是一个旧版本的组，按预算替换。改版本和「决定建」两个写以同一个 resourceVersion 分先后 | 旧版本的组留着不换；已经有 Pod 的组被改了版本 |
| 要替换的正式的组，删掉之后低位补不上：替代的容量得按基线建而基线读不到；小于 N 的序号被外来的对象占满了 | 跳过它，接着看下一个候选；候选都补不上时报 `BaselineUnknown` 或 `OrdinalOccupied`，这时不算有滚动要做：不建 surge，已有的 surge 被回收。两个范围外的组指望同一个空闲序号时只删一个。序号小于 N 的带标记的组也算着落：删掉一个正式的组之后它转正 | 删了之后一直少一个组 |
| 基线读不到期间的范围外空组 | 留着，版本不改。副本数调回来之后它是有成员的旧组，不替换；基线读到之后被替换，替代的容量在低位按基线建。终局与基线一直读得到时相同 | 按新版本起并且留下 |
| `RoleRecreate` 清空了组里全部 Pod（每组只有一个实例） | 按组自己的版本重建：写 Creating 的那一次把要建的个数记进 `status.pods`，组不算没有成员 | 版本被不占预算地改掉 |
| P = N 的停点上把模板改回基线（NEW-8） | 序号都小于 P，中间版本的组不动，直到 P 调小。与契约相同；上一版在这里要批准一条条款 | 中间版本的组被换回去 |
| 基线读不到 | 保护照常。要用基线建组、要把没有成员的组改成基线、要替换序号小于 P 的组、要替换一个替代的容量得按基线建的组，这四种都不做，报 `BaselineUnknown`，等待。正式的组不跳到更高的序号上去建 | 猜成最新版本 |
| 带 surge 标记的组失败 | 只由 G1 删，回收不能绕过「等故障成员消失」。序号小于 N 时转正照常适用 | 被回收的规则直接删掉 |

### 10.6 升级接管

[06](06-live-upgrade.md)。接管本身不创建、不删除健康的 Pod。接管期间会发生的创建和删除有三类，都是设计要做的：带旧版本删除标记而还活着的存量 Pod 按 UID 删掉（06 的 T2）；实例不齐的补；已经换完 owner 的组由 ServingGroup controller 照常做 Role 一级的事（组内没滚完的滚动接着滚，终态的 Pod 按策略恢复）。

必须判错的：除上面三类之外，接管期间有健康的、不带删除标记的 Pod 被删除或者重建；滚动中带 surge 的组接管之后成了正式的组。

### 11.1 要批准的 5 条

**C1、C2 的来历。**这两样是契约 2.8 有过、2.9 删掉的要求（契约 `docs/specs/README.md` 的修订记录）。2.8（2026-10-09）：「空组、surge身份、故障计时与创建事实保留」。2.9（2026-10-09）：「按用户明确取舍，整体移除私有成员 ConfigMap，五类成员表不迁移到 status/owner annotation。新进程或主备接管重新起算故障宽限，允许重启期间删除事件丢失并按当前事实补缺……本条取代下述历史 2.4/2.8 的故障计时及空组/创建事实保留要求」。所以 C1、C2 是撤回 2.9 那一次取舍里的两样：创建事实的保留，和离线的丢失只补。故障计时那一样不撤回：新进程重新起算故障宽限，与 2.9 相同（D9）。

2.9 取舍的对象是一个私有的成员 ConfigMap 和五类成员表。这一版的载体不同：一个公开的 CR 的 `status`，只有一个写者，零值不引起删除（02 的 L2）。当时的顾虑里仍然成立的：多一张要维护的表；表被清空或者改写的后果（03 的 10.5）；成员 Pod 的状态每变一次，组的 `status` 写一次。

C1 不能不批：没有它这份设计不成立。C2 用户已经给出口径并确认，见表后。

**C2 的范围**（用户 2026-11-23 的口径）。升级 controller、主备切换、多副本时主被删或者主所在的节点故障，算在正常运行的容灾范围里，不赦免：这期间丢了 Pod，照 `recoveryPolicy` 的范围处理。赦免的是 controller 完全故障，和 controller 被删除之后发生的变化：这两种允许只补；照范围恢复也可以，口径只是指出必须覆盖的情形，不要求为了只补去做复杂的设计。用户随后说明：真实部署都是多副本并且开启选主，单副本或者手动把副本数调成 0 按故障处理；单副本部署下的升级和重启也按故障处理。对照：

| 情形 | 口径 | 今天的两个版本 | 这一版 |
| --- | --- | --- | --- |
| 升级 controller（新版本到新版本） | 不赦免。前提是多副本并且开启选主 | 空窗里丢的只补 | 按范围恢复 |
| 主备切换（含同版本滚动重启、主的进程重启引起的）；多副本时主被删、主所在的节点故障 | 不赦免。前提同上 | 切换的空窗里丢的只补 | 按范围恢复 |

所以 C2 已经定下来：前两行是要求，第三、四行可以，第五行的缺口接受。契约 2.9、2.11 里「重启期间」「离线」的说法要按口径收窄到完全故障和被删除。这是契约的修订，在 runner 的仓库里做成了契约 2.13（工作区任务 009），不在本目录里。2.13 的归类与上表相同。第三行里只有一个副本时的重启和升级也按故障，用户已确认。这一版对每一行都按范围恢复。

**grace 的计时不在这个口径里。**用户（2026-11-23）：grace 的计时可以赦免，因为它只影响时间，恢复直接影响 Pod 的真实生命周期。所以重启故障的起点留在进程里，新进程重新计满一个 grace，与契约 2.9 和已批准的 D9 相同。上一稿列过一条 N1（把起点写进账本，换主之后接着算），撤回：它要改契约里的 7 处文字，账本多一个带身份的字段，停机超过 grace 时回来第一轮到期的范围同时恢复。

「重启之后重新计 grace」今天没有可执行的用例保护：行为分析解析了 `cases/` 下全部 717 个 RUN 文件，另看了 `recovery-contract` 的 7 条断言和 RC-01–04 的执行脚本，断言这一条的是 0 例；带有限 grace 的用例和带 controller 重启、换主的用例没有交集。契约自己的说法是「有限 grace 重启计时与插件边界缺专项验证」。第 8 节的 NT18、NT19 补上。

## 13. 没有验证的

- 全部结论是推论，没有在集群上运行。重放的是组一级的规则函数，不是 controller。
- 场景重放的环境里，一个组的删除是「标成终止中，之后整个消失」；没有「对象还在、Pod 已经没了」的中间态，没有两个 controller 之间的那一跳。行为分析的重放没有比停点的 `blocked`；模拟器的重放比了（05 的 2.2）。
- 同名的 PodGroup、Service 先删后建时，Volcano、kube-proxy、DNS 的反应。
- 垃圾回收器的延迟和停摆；每换一个组多出来的两跳要多久。
- `kubectl wait` 在同名重建时的行为。
- `normal` 套件 SG 模式的 68 例由模拟器逐例重放过，在组一级。组里 Pod 的个数、worker 的布局、PodGroup 没有核对；runner 的放行方式是从用例的文字和结构读的，runner 的源码不在导出里。
- Role 一级没有重放。附录 B.6、契约 2.10、RC-02 到 RC-04 因此没有独立核对。
- 晚一跳的 37 例时序用例：机制变了（复核），没有在集群上验证。复核和直读的代价（每个有写的轮次一次 LIST；成员 Pod 的状态每变一次，它的组一次 status 写）没有测量。
- 契约自己不一致的 8 例等裁决；`history-sparse` 的 6 例可能是同一处，没有核对。
- `lost-deletion` 的 SG 模式 3 例：同名重建之后，成员名字被缓存里上一代的 Pod 占着时靠直读确认（02 的 L7）。是推演。
