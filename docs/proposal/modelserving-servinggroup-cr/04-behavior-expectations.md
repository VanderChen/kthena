## 5. 恢复：策略 × 触发

已建成的 Role 实例（账本是 Established）。

| 触发 | `None` | `RoleRecreate` | `ServingGroupRecreate` |
| --- | --- | --- | --- |
| 成员被删除（controller 在场） | 补这一个 | 重建这个实例 | 换掉整个组 |
| 成员被删除（controller 不在） | 补这一个 | **重建这个实例**（契约：只补） | **换掉整个组**（契约：只补） |
| 成员是 `Failed`、`Succeeded` | 删这一个再补（D10、D13） | 重建这个实例，不等 grace（D13） | 换掉整个组，不等 grace |
| 重启故障，grace ≥ 0 | 只报告 | 满 grace 之后重建这个实例 | 满 grace 之后换掉整个组 |
| 重启故障，grace 是 `-1` | 只报告 | 只报告 | 只报告 |
| 未就绪，没有重启 | 等待 | 等待 | 等待 |

创建中的 Role 实例（还没有写上 Established）：成员被删除一律只补，三种策略相同。契约在连续运行时按范围恢复；在网版本连续运行时已经是只补。

首次补建用什么版本（契约 API 参考 6.1 的表，已应用 v1、目标 v2）：

| 滚动模式 | 恢复范围 | 契约 | 本设计 |
| --- | --- | --- | --- |
| ServingGroup | `None`：补一个 Pod | 这个组已应用的 v1 | 相同：组的 `spec.revision` |
| ServingGroup | `RoleRecreate`：一个实例 | 这个组的 v1 | 相同 |
| ServingGroup | `ServingGroupRecreate`：整个组 | 按它的序号和当前 partition | 按数量：非目标的组少于 P 时用基线，否则用目标。失败的组是受保护的组之一时结果相同（少了一个非目标的组，补基线）；是不受保护的组时结果相同（补目标）。只有受保护的集合按序号和按数量不同的时候才不同，例如停机期间改了 P（RC-01） |
| Role | `None`：补一个 Pod | 这个实例已应用的 v1 | 相同 |
| Role | `RoleRecreate`：整个实例 | 按 Role 的序号和 partition | 相同，Role 一级仍按序号 |

## 6. 重启之后的删除续行（契约 2.11）

| 重启时的事实（契约） | 契约的处理 | 本设计 | 结论 |
| --- | --- | --- | --- |
| 有删除标记的 Role 或 ServingGroup | 把还在的标记了的原 UID 删完；Ready 不撤销 | 实例：账本是 Draining(g)，接着删代际号不大于 g 的。组：Failed 加 Drained 则删组，已经在终止中则由垃圾回收器删完。Ready 不撤销 | 一致。载体不同（X8） |
| 原范围里出现同名的新 UID | 留下，不吸进旧批次 | 实例：新 Pod 的代际号是 g+1，不在范围里。组：新组的名字不同 | 一致 |
| 没有标记，只看到离线缺员 | 按当前数量和历史模板补，不扩大范围 | 已建成的实例：按范围恢复。创建中的：补 | **有意变化**（X6） |
| 原 Pod 还在终止 | 等它消失 | 相同 | 一致 |

RC-01 到 RC-04（恢复中断后重启）：

| 用例 | 契约 | 本设计 | 结论 |
| --- | --- | --- | --- |
| RC-01　SG 模式，`ServingGroupRecreate` | 组 0 的剩余成员删完，全部换 UID；按历史 A 重建；之后组 1 滚成 B | 新进程读到组 0 是 Failed：清空之后删掉，级联删其余成员；补一个新的组，版本按数量。过程表见 04a 的 RC-01 | **有意变化**（X2、X7）：替换的组直接用 B，组 1 在 P=1 的阶段不动。另外健康成员是垃圾回收器删的，runner 的故障代理拦不到，切点要改成拦组的 DELETE |
| RC-02　SG 模式，`RoleRecreate` | prefill 实例 0 剩下的 entry 删掉，entry 和 worker 都换 UID；同组的 decode、组 1 不动 | 账本里这个实例是 Draining(g)：新进程接着删 entry，清空，写 Creating(g+1)，按这个组的版本重建，写 Established | 一致。切点的证据从「Pod 上有标记」换成「账本是 Draining」 |
| RC-03　Role 模式，`RoleRecreate` | 同上，重建按 Role 的 partition | 同上；Role 一级的 partition 仍按序号 | 一致 |
| RC-04　协调 Role | 同 RC-03，不多给预算、不跳过 | 同上；协调的规则没有变 | 一致 |

## 10. 契约里没有的场景

本设计需要、契约没有的场景。预期写在这里，过程表在 04a 第 2 节或者 03。

| 场景 | 预期 | 必须判错的 |
| --- | --- | --- |
| 整组恢复（NEW-1） | 组写上失败；故障成员消失之前其余成员继续运行；之后组被删；Pod 都消失之后才建替换的组，名字是新的 | 故障成员还没停就删其余成员；失败的组还在时就建了替换的（没有滚动在进行时） |
| 灰度停点上一个组失败（NEW-2、NEW-3） | 替换的组的版本按数量：非目标的组少于 P 用基线，否则用目标 | 用错版本 |
| 多建了一个组（NEW-4） | 没有过期的组时上限是 N：缩回，未就绪的、最新的先 | 删了健康的老组 |
| 滚动中一个旧组失败（NEW-5） | 失败的组被删；预算照算 | Ready 被替换拉到 `minAvailable` 以下 |
| 任何一次写之后换主 | 03 的 10.2：新进程的动作与原进程相同，或者按更新的事实 | 新进程删了原进程不会删的健康成员；重复创建组（单进程） |
| 两个进程并存 | 可能多建组、钩子重复；旧的一边退出之后收敛 | 用旧的 Draining 删掉新一批的 Pod；把创建中的实例当成丢失 |
| `spec` 刚下发（EX-3） | 未观测的组不被替换 | 把未观测当成未就绪去删 |
| 升级接管 | [06](06-live-upgrade.md) 第 6 节 | 接管期间任何 Pod 被创建或删除 |

## 11. 碰到的契约条款

设计在字面上与契约 2.12 不一致的条款。**这些要逐条批准；批准之前不改 runner 的文档和用例。**

| # | 契约的条款 | 本设计 | 条款背后的意图还成立吗 | 要批准的 |
| --- | --- | --- | --- | --- |
| C1 | 「不创建成员 ConfigMap 或等价 status/owner annotation 表」（A.5、2.9） | `ServingGroup.status.roleInstances[]` 是逐实例的表，Established 就是「创建事实」 | 2.9 不要的是那张私有的表和它的复杂度，代价是离线丢失只补。这里的表每项三个值加一个代际号，没有故障时间，写在一个公开的 CR 上 | ServingGroup 上持久化每个 Role 实例的建成记录 |
| C2 | 「重启期间的删除事件允许丢失」「无标记的离线缺失仍补缺，不凭缺员扩大恢复范围」（2.9、2.11、A.4） | 已建成的实例丢了成员，回来之后按范围恢复 | 2.9 是为了不持久化而接受的结果。但「不扩大范围」是写明的预期 | 旧：controller 停着时丢一个 Pod，回来只补这一个。新：`RoleRecreate` 重建整个实例，`ServingGroupRecreate` 换整个组。升级 controller 时如果同时在排空节点，重建的 Pod 比以前多 |

| C4 | 「主动删除前标记原选定 Pod……不引入 operation、阶段」（2.11） | 没有 Pod 标记；账本有一个阶段（Draining）加代际号 | 三条意图都成立：重启后把原范围删完；范围内健康的也删；不吸纳同名的新 UID | 用账本的阶段取代 Pod 注解 |
| C5 | 「partition 是绝对 ordinal 阈值，不是任意保留若干实例」（0.5、A.2、API 参考 3.3） | 组一级保留次序最靠前的 P 个非目标的组 | 意图是用户能预期哪些单元留在旧版本、新建的是什么版本。按数量之后前者只能预期个数 | 02 的 4.3 的五条定义；同一个 API 里两层 partition 语义不同 |
| C6 | 稀疏序号、补洞、身份债的全部条款（0.6、A.3、A.5） | 没有对象 | A.1 的取舍次序里前两条（不扩大可用性缺口、不重建健康且无需更新的组）都守住；第三条（排齐）不再存在 | 这些条款对组一级作废 |
| C7 | 临时 surge 的身份、转正、「滚动完成须临时 surge 已清理」（0.6、0.7、A.2、D1） | 没有临时身份。个数等于 N 就是完成 | 不误删有用的组：成立并且更强。不让临时容量长期占着：成立，没有过期的组时上限是 N | 每次滚动少建少删 S 个；D1 不再适用；SG-C16 的终态 |

## 12. D1–D15 本身与契约 2.12 的差别

005 是按契约 2.7 写的。下面的差别在本设计之前就有，本设计沿用 005 的决定。

| 决定 | 与契约 2.12 |
| --- | --- |
| D10、D13：`Failed`、`Succeeded` 的 Pod 在所有策略、所有 grace 下等同于被删除的 Pod | **不同。**契约：`None` 下不因 `Failed` 主动删除；`-1` 永久容忍 `Failed`；正数 grace 对 `Failed` 同样计时；`Succeeded` 不是触发条件 |
| D11：已经开始的恢复在策略改成 `None`、`-1` 之后仍然做完 | 与 API 参考 6.2「切到 None/-1 必须取消」不同 |
| D14：不做退避 | 与 A.4 第 3 条「不反复重建同版」有冲突，005 标为待讨论 |
| D1、D2、D3、D9、D15 | 相同 |

## 13. 没有验证的

- 全部结论是推论。脚本重放的是组一级的规则函数，不是 controller。
- 用例目录里逐例推演过的只有 35 个组合场景、RC-01 到 RC-04 和十几个点名的用例。`normal` 套件里滚动途中扩缩容的一段（115 例）每例的在途时序不同，按规则归类可能偏乐观。
- 「一致」的 Role 一级场景依据的是「规则原样搬过去」，没有 Role 一级的重放。
- X9 的窗口有多长、X18 的 PDB 行为，都没有在集群上看过。
