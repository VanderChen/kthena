## 0. 文档信息

| 项 | 内容 |
| --- | --- |
| 用途 | 回答「换成这个设计之后，哪些行为变了，哪些没变」。先列出行为会出现差异的点，再推出其余场景是否一致。结论用 runner 那样的过程表承载，过程表在附表 [04a](04a-scenario-process-tables.md) |
| 对照的基线 | 行为契约 2.12（`kthena-rollout-runner` `main` @ `3772012`，2026-11-09）：`docs/specs/servinggroup-compound-rollout.zh-CN.md`、`modelserving-api-reference.zh-CN.md` 和 `cases/` 下的全部套件。契约之后批准的 D1–D15（[005](../modelserving-rollout-final/README.md)）与契约不同的地方单列在[第 12 节](#12-d1d15-本身与契约-212-的差别)，不算在本设计头上 |
| 怎样得出 | 组一级的场景：把场景写成脚本，在本设计的规则函数上重放，过程表和结论由脚本生成（[05](05-inference-verification.md) 第 2 节）。Role 一级的规则没有变，靠推演。本文和 04a 里的生成部分由任务目录的 `model/build_docs.py` 写入并校验 |
| 证据的类别 | 三类，结论旁边注明。**模拟器重放**：任务目录 `model/` 的场景脚本和停点脚本，结果由脚本生成并校验。**复核的重放**：两份评审各自用同一个规则函数单独算的例子，脚本没有留下，结果记在任务目录 `subagents/` 的评审报告里。**推演**：按规则读出来的，没有执行。第 3、4 节的生成块是模拟器重放；手写部分没有注明的是推演 |
| 状态 | **全部是推论，没有在集群上运行。**没有修改 runner 的文档和用例。碰到契约条款的地方集中在[第 11 节](#11-碰到的契约条款)，等批准 |
| 结论的取值 | **一致**：可观察的行为相同，只有组和 Pod 的名字不同。**有意变化**：至少一项可观察量不同，原因写明。**不适用**：场景的前提在本设计里建立不起来。**待定**：留给真实验证 |

「可观察量」指改名之后还能比的东西。结论只比五项：创建了几个组、删除了几个组、哪些原有的组保住了身份（UID）、终态各版本的个数、终态就绪数。五项全部相同记为一致。

过程不在这五项里。过程上有的证据和没有的：

| 过程上的量 | 怎样处理 |
| --- | --- |
| Ready 的下界、活动数的上界 | 脚本在每次替换健康的组时检查 Ready 不低于 `minAvailable`，违反就报错。每段的最低 Ready 和最高活动数只打印，不与契约比；评审把其中 25 个结论是「一致」的场景与契约的过程表手工对过，没有发现不同 |
| 停点（缩容做完才开始替换） | 五个 runner 用例的停点单独重放：SG-C02、C05、C07、C10、C12（[05](05-inference-verification.md) 第 2 节的生成表）。其余场景的停点没有逐步比 |
| 同一轮里动作的先后、事件到达的先后 | 不比。模拟器只走一条固定的次序：执行整份计划，全部删除完成，全部新组就绪。已知的差别列在第 3 节 |

## 5. 恢复：策略 × 触发

已建成的 Role 实例（账本是 Established）。

| 触发 | `None` | `RoleRecreate` | `ServingGroupRecreate` |
| --- | --- | --- | --- |
| 成员被删除（controller 在场） | 补这一个 | 重建这个实例 | 换掉整个组 |
| 成员被删除（controller 不在） | 补这一个 | **重建这个实例**（契约：只补） | **换掉整个组**（契约：只补） |
| 成员是 `Failed`、`Succeeded` | 删这一个再补（D10、D13） | 重建这个实例，不等 grace（D13） | 换掉整个组，不等 grace |
| 重启故障，grace ≥ 0 | 只报告 | 满 grace 之后重建这个实例 | 满 grace 之后换掉整个组 |
| 重启故障，grace 是 `-1` | 只报告 | 只报告 | 只报告 |
| 未就绪，没有重启 | 等待 | 等待 | 等待 |

controller 不在时的丢失有一个例外：从旧版本升级上来的第一次，账本从零值开始，停机期间丢的只补（[06](06-live-upgrade.md)）。已建成的实例里正在终止的成员也算丢失。

创建中的 Role 实例（还没有写上 Established）：成员**被删除**一律只补，三种策略相同。成员是 **`Failed`**（以及上表里别的故障）仍然按上表的范围恢复（03 的 4.3 的 E5）。两者在实例建成之前的结果因此不同：API 驱逐是删除，只补；节点压力驱逐留下的是 `Failed` 的 Pod，按范围恢复。对被删除的成员，契约在连续运行时按范围恢复；在网版本连续运行时已经是只补。

首次补建用什么版本（契约 API 参考 6.1 的表，已应用 v1、目标 v2）：

| 滚动模式 | 恢复范围 | 契约 | 本设计 |
| --- | --- | --- | --- |
| ServingGroup | `None`：补一个 Pod | 这个组已应用的 v1 | 相同：组的 `spec.revision` |
| ServingGroup | `RoleRecreate`：一个实例 | 这个组的 v1 | 相同 |
| ServingGroup | `ServingGroupRecreate`：整个组 | 按它的序号和当前 partition | 按数量：失败的组消失之后，非目标的组少于 P 时用基线，否则用目标。灰度已经滚到停点时与契约相同：受保护的组失败，补基线（NEW-3）；目标版本的组失败，补目标（NEW-2）。**灰度还没滚完时受保护的组失败**，与契约不同：剩下的非目标的组仍然不少于 P，替换的组用目标，另一个还没轮到的旧组成为受保护的那一个。留在旧版本的个数相同，是哪一个组不同，比契约少建一个（NEW-7）。停机期间改了 P（RC-01）是同一类 |

受健康额度晚一跳影响（X9）的用例是 5 例。它们的期望都是「下一次主动删除按最新的可用量重新计算」：

| 用例 | 归类 |
| --- | --- |
| `eviction` RUN-433、`midrollout-faults` RUN-403 | 待定 |
| `midrollout-faults` RUN-407、411，`rollout-blocking` RUN-616 | 有意变化（带 X4）。时序上有同样的风险 |

可验收的界是瞬时的：任一时刻真实就绪的组数不低于 N − U − 状态还没有写出来的组数；一轮计划里多删的健康的组不超过 U + S；`status` 写出来之后的计划不再多删。这 5 例里各只有一个组失去就绪，所以是至多比下限少一个。几个组同时落后时缺口更大：N=4、U=2，两个组同时失去就绪而都还没报告，这一轮删掉两个健康的组，真实就绪 0 个。它不是累计的界：同一个组一直落后时，每建好一个新组就再删一个旧组；N=3、U=0、S=1，一个组一直落后，累计删掉三个健康的旧组，每次删之后真实就绪都是 2。瞬时的界在带滞后的穷举模型里成立（[05](05-inference-verification.md) 第 3 节的 L1、L2），累计的例子是评审的重放。窗口有多长、这 5 例在窗口里会不会碰到，留给真实验证（[05](05-inference-verification.md) 第 7 节）。

## 9. plugin 调用点

框架的四个钩子按调用点的变化分析，在 [02](02-design.md) 第 7 节。特定实现的 plugin 不分析。对 `plugin-retry` 套件的 4 例：

| 用例考的 | 变化 |
| --- | --- |
| `OnPodCreate`、`OnRoleSync` 失败之后重试 | 调用者换了，重试的方式不变（这一轮出错，下一轮再来） |
| `OnRoleDelete` 失败 | 今天在 Pod 的 DELETE 发出之后调，失败不挡删除。这里实例被清空时在删 Pod 之前调：调之前直读复核账本仍是 Draining，`HookRequest` 带代际号；失败则这一轮不删，下一轮重试；一直失败时实例停在清空中，挡住恢复、Role 缩容和按重建的 Role 滚动。整组删除时只尽力调一次，失败不重试 |
| SG 模式的 RUN-536、537 | `ServingGroupRollingUpdate` 下滚动、缩容、整组恢复全是整组删除，`OnRoleDelete` 在这个模式下从来不保证调到。用例注入「连续失败 2 次再恢复」之后不会再有重试；期望里的「不泄漏旧的和多出来的资源」要靠 plugin 的资源挂在 ServingGroup 名下、由垃圾回收清掉 |

## 10. 契约里没有的场景

本设计需要、契约没有的场景。预期写在这里，过程表在 04a 第 2 节或者 03。NEW-1 到 NEW-10 是模拟器重放：没有契约一侧可比，脚本只检查预算。其余各行是推演。

| 场景 | 预期 | 必须判错的 |
| --- | --- | --- |
| 整组恢复（NEW-1） | 组写上失败；故障成员消失之前其余成员继续运行；之后组被删；Pod 都消失之后才建替换的组，名字是新的。S > 0 并且滚动在进行时不等它消失，用 surge 的名额先建（X20） | 故障成员还没停就删其余成员；失败的组还在时就建了替换的（没有滚动在进行时） |
| 灰度停点上一个组失败（NEW-2、NEW-3） | 替换的组的版本按数量：非目标的组少于 P 用基线，否则用目标 | 用错版本 |
| 灰度还没滚完时受保护的组失败（NEW-7） | 替换的组是目标版本，另一个还没轮到的旧组成为受保护的那一个；一共建 1 个 | 替换的组用了基线，另一个旧组又被滚掉（多一次重建） |
| 多建了一个组（NEW-4） | 没有过期的组时上限是 N：缩回，未就绪的、最新的先 | 删了健康的老组 |
| 滚动中一个旧组失败（NEW-5） | 失败的组被删；预算照算 | Ready 被替换拉到 `minAvailable` 以下 |
| 各 Role 的副本数都是 0 时提交新版本，再调回来（NEW-6） | 空组的版本按新建的规则重新指派：P 个名额给基线，其余改成目标版本。对象和名字不变，不占预算。调回来时各组按自己的版本建 Pod | 空组被删掉重建；调回来时先按旧版本建 Pod 再被替换 |
| 空组：P 调大之后，目标版本的空组回到基线（NEW-9）；受保护的是中间版本时回到基线（NEW-10） | 各版本的个数与契约按序号新建的结果相同。有 Pod 的组不会这样改版本 | 有 Pod 的组被改了版本；个数与契约不同 |
| P = N 的停点上把模板改回基线（NEW-8） | 目标等于基线，没有受保护的组：中间版本的组按预算换回基线。等批准（C5c） | 换回去的过程里 Ready 低于 `minAvailable`；与批准的结果不符 |
| 任何一次写之后换主 | 03 的 10.2：新进程的动作与原进程相同，或者按更新的事实 | 新进程删了原进程不会删的健康成员；重复创建组（单进程） |
| 两个进程并存 | 可能多建组、钩子重复；旧的一边退出之后收敛 | 用旧的 Draining 删掉新一批的 Pod；把创建中的实例当成丢失 |
| `spec` 刚下发时提交新版本（EX-3） | 未观测的组不被替换 | 把未观测当成未就绪去删 |
| `spec` 刚下发时缩容 | 按报告的就绪排：上一次报告未就绪的组先删 | 删了健康的组，留下上一次已经报告未就绪的组 |
| 用户直接删一个组 | 02 的 5.5 | 多出来的组不缩回；`--cascade=orphan` 留下的成员 Pod 被删，或者长期没人管 |
| 升级接管 | [06](06-live-upgrade.md) 第 6 节 | 接管期间任何 Pod 被创建或删除 |

| C12 | 「切到 None/-1 必须取消旧任务的删除效果」（API 参考 6.2） | Failed、Draining 写上之后不撤销（X15） | D11 已经批准「已经开始的做完」。这里把例外从「已经开始」扩大到「已经提交」 | 例：grace 到期，组写上 Failed，第一个 Pod 还没删，用户把 `recoveryPolicy` 改成 `None`。旧（005 的 M6）：撤销，一个 Pod 都不动。新：整组照删。还在等 grace、没有写上 Failed 或 Draining 时改策略仍然可以取消，这一点没有变。评审可以选的另一种做法：组还没进入终止中时，G1 删除之前按最新的策略复核一次；代价是提交点后移一步，接管表多一行 |
| C13 | 「优先在原 ordinal 重建」；连续布局滚动之后序号仍是 `[0, N)`（A.3、API 参考 3.2） | 随机名字下没有序号。序号命名下（LWS 路径、回退窗口内）新组取最小的空闲序号，多出来的组不回收，集合可以有洞 | 身份稳定这个意图在随机名字下不成立。序号命名下「滚动之后回到 `[0, N)`」在 S > 0 时不成立 | 随机名字：X1。序号命名的例：N=3、S=1、U=0，回退窗口内滚一次。旧：结束时序号是 `{0, 1, 2}`。新：`{1, 2, 3}`。LWS 路径上 S 取 0，滚动不留洞；缩容按未就绪、deletion cost 选，会留下洞，`group-index` 可以不连续，这一点今天也是这样 |
| C14 | 「实际活动单元数不超过期望副本数 + maxSurge……创建预约也不能漏记」（0.3）；容量上限是活动的组数不超过 `desiredReplicas` + `maxSurge`（A.2）。每一步成立，runner 在每个 Pod 事件上检查 | 单进程、没有人手工删组时每一步成立。四种情形会超，事后缩回：升级接管时整个组都在终止而没有被接管，闸门放行之后按数量补了一个，新旧两批 Pod 短时间并存（[06](06-live-upgrade.md) 的 5.2）；两个进程并存；原进程退出之后它发出的创建请求才落地；用户用后台方式删一个组，组对象立刻消失，它的 Pod 还在终止，新组已经在建（02 的 4.5、5.5、6.4） | 意图是任何时刻占用的容量有上界。部署前提之下前两种不出现在正常运行里；出现时多出来的组是最新的、多半未就绪，下一轮缩回，健康的老组不动，但它带着 PodGroup 进过调度队列。第三种是用户的动作 | 旧：每一步成立。新：单进程、没有人手工删组时每一步成立，其余情形最终成立 |

r0 草稿里另有三处按字面会碰到契约的地方，在终稿里已经改掉，不需要批准：基线在灰度停点上推进（现在是 v2 的 R17）；既不是基线也不是目标的组被换回基线（现在保护非目标的组，EX-1）；缩容没做完就开始替换（现在等 `active` 不超过 `cap`；代价是 N 调小之后，卡住的终止中的组或清不空的失败组会挡住滚动，报 `WaitingForDeletion`）。

评审之后又改掉三处，同样不需要批准：受保护的基线组被重建之后，留下的变成中间版本（现在基线版本的先受保护，EX-4）；全零的过期组扩回来时先起旧版本（现在直接改版本，NEW-6）；`status` 的计数和 `Available` 的含义与当前实现不同（现在回到当前实现的口径，X17）。

## 12. D1–D15 本身与契约 2.12 的差别

005 是按契约 2.7 写的。下面的差别在本设计之前就有，本设计沿用 005 的决定。

| 决定 | 与契约 2.12 |
| --- | --- |
| D10、D13：`Failed`、`Succeeded` 的 Pod 在所有策略、所有 grace 下等同于被删除的 Pod | **不同。**契约：`None` 下不因 `Failed` 主动删除；`-1` 永久容忍 `Failed`；正数 grace 对 `Failed` 同样计时；`Succeeded` 不是触发条件 |
| D11：已经开始的恢复在策略改成 `None`、`-1` 之后仍然做完 | 与 API 参考 6.2「切到 None/-1 必须取消」不同 |
| D14：不做退避 | 与 A.4 第 3 条「不反复重建同版」有冲突，005 标为待讨论。不退避的代价在本设计下更显眼：`ServingGroupRecreate` 下一个起来就 `Failed` 的组被反复换掉，每一轮是一个新的 ServingGroup、新的 PodGroup 和一批新的 Pod 名，事件不再按名字聚合，按 Pod 名的监控序列一直增长。005 留下的「要不要加恢复次数的指标」因此更值得定下来 |
| D1、D2、D3、D9、D15 | 相同。D1 在组一级不再适用（C7） |

## 13. 没有验证的

- 全部结论是推论，没有在集群上运行。脚本重放的是组一级的规则函数，不是 controller。
- 「一致」只比五项可观察量（第 0 节）。停点只有五个 runner 用例单独重放过；事件到达的先后只走了一条。
- 用例目录 1013 项里，按终稿的规则看过的是 220 项：36 项模拟器重放，184 项复核逐例读过。其余 793 项里，2 项按终稿的规则归类而没有逐例读，791 项沿用起草前的归类（第 8 节）。`normal` 套件「滚动过程中扩缩容」一组 115 例每例的在途时序不同；其中 SG 模式 57 例，复核读过 15 例，其余按规则归类，可能偏乐观。
- `recovery` 套件 84 例里的「暂停 controller」是按「故障代理拦请求、进程没有重启」读的。导出的目录里没有 runner 的源码，没有核对。如果是停进程，带 `RoleRecreate`、`ServingGroupRecreate` 的那些用例是 X6 的有意变化，有意变化会多出几十例。
- 「一致」的 Role 一级场景依据的是「规则原样搬过去」，没有 Role 一级的重放。附录 B.6、契约 2.10、RC-03、RC-04 因此没有独立核对。
- X9 的窗口有多长、5 例时序用例的界（第 8 节）、X18 的 PDB 行为、X20 各处的耗时，都没有在集群上看过。
- X17 的计数和 condition 是按定义推演的，没有模型。空组的版本重新指派（NEW-6、NEW-9、NEW-10）只有场景重放，没有进穷举模型。序号命名不在规则函数里，C13 的例子是推演。
