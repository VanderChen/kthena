## 1. 结论

现规范的预算、版本和候选顺序规则站得住，建议保留。问题集中在身份规则上。为了少重建一个单元，现规范引入了保留组与临时组的持久化身份、surge 转正条件、surge 与范围外旧组配对补洞、身份债、在途额度账本五个概念。其中配对补洞要预判后续的删除才能决定，转正条件里的「能承接正式容量」没有可判定的定义，在途额度账本有一部分无法从集群状态看出来。

修订规则把身份规则换成一句话：**surge 单元带一个标记，只创建在序号 ≥ N 的位置，用完删除。**其余的身份概念都可以由这个标记和序号推出来。

相对现规范的改动有六处。

1. **surge 的位置和身份只由标记和序号决定。**不再有配对补洞和身份债。正式单元永远补 `[0, N)` 里最低的空位，surge 永远建在 N 以上。
2. **取消在途额度账本。** `inFlightReservations` 改为「只统计没有在删除的单元」。现规范附录 B 里带数值的 35 行，结果逐行相同。
3. **删除两条规则，改写一条。** 删除的是 surge 与范围外旧组配对补洞（A.3 第 4 条）、受保护槽位补建期间继续占在途额度（API §2.3）。改写的是 surge 转正（§0.6）：现规范的条件「能承接正式容量」没有可判定的定义。
4. **把操作偏序写成固定阶段。** 缩容、补正式单元、临时容量、替换，四个阶段每轮按序执行，外加一条门控：缩容没结束时不开始替换。
5. **SG 模式下修改 `roles[].replicas` 不再分批应用**（SG-R01）。
6. **新增 InPlace 规则。** 现规范没有任何一处描述原地升级。

另有一处，草案正文是按任务输入的选择写的，本文建议改回去：**N 扩大后覆盖了已有的 surge 时，草案不转正**，把它原位重建成正式单元。分析下来，它需要给另外两条规则开例外，U 为 0 且集群没有余量时还会卡住，并没有换来可读性。详见 D1。规则正文里受这个选择影响的只有 R3 和 R11(b)，以及 6.2 的三个场景。

## 2. 设计原则

修订规则按下面的优先级取舍，前一条优先于后一条。

1. **可用性底线和容量上限不被滚动突破。**
2. **序号可预期。** 除显式缩容外，任何操作都不新增空洞。
3. **规则可由当前状态判定。** 一条规则只使用最新 spec 和集群里当前可见的信息，不依赖 controller 进程内的记忆。预算、候选和阶段规则（R1～R29）都满足这一条；故障恢复有三处做不到，列在 [4.10](#410-故障恢复与重启)。
4. **少重建。**

现规范的优先级是「可用性与容量 > 不重建健康单元 > 规模收敛与补洞」（A.1）。修订后「少重建」从第二位降到第四位，这是两份规则的根本差别。

三个词在本文里的含义如下，后面的判断都以它们为准。

| 词 | 可判定的定义 |
| --- | --- |
| 保序 | 两层意思。序号集合：在稳定检查点上，空洞数只会因显式缩容而增加；从 `[0, N)` 出发、不含显式缩容的操作序列，结束时仍是 `[0, N)`。动作顺序：阶段顺序固定，同类候选按序号从高到低 |
| 浪费 | 创建后又被删除的单元。本文用「相对现规范多创建、多删除的单元数」计量 |
| 可读性 | 一条规则能否只用下列信息判定：最新 spec、单元的序号、版本标签、surge 标记、是否 Ready、是否正在删除 |

## 3. 模型与术语

**单元**是滚动的最小单位。`ServingGroupRollingUpdate` 下是一个完整的 ServingGroup；`RoleRollingUpdate` 下是某个 ServingGroup 内某个 Role 的一个实例（1 个 entry 加它的全部 worker）。下面的规则对两者相同，只是 N、U、S、P 取各自生效层的值，Role 模式在每个 ServingGroup 内、每种 Role 上独立计算。

| 符号 | 含义 |
| --- | --- |
| N | 最新期望副本数。SG 模式取 `spec.replicas`，Role 模式取该 Role 的 `replicas` |
| U、S、P | 生效层的 `maxUnavailable`、`maxSurge`、`partition` 解析后的整数 |
| 目标版本 | 最新模板对应的 revision |
| 基线版本 | 最近一次全量完成的 revision，即 `status.currentRevision` |

每个单元有四个可观察属性：序号、版本、是否 Ready（全部必需成员 Ready）、是否正在删除（删除请求已被接受，对象还没消失）。另有一个属性在创建时写入、之后不变：**surge 标记**。

按标记和序号，单元分成三类。

| 类别 | 判定 | 来源 |
| --- | --- | --- |
| 正式单元 | 不带标记。其中序号 ≥ N 的称为范围外正式单元 | 初始创建、扩容、替换。范围外的只可能来自显式缩容（按健康度或 deletion cost 选中了低位单元，高位的留了下来） |
| 临时单元（surge） | 带标记，序号 ≥ N | 滚动期间创建 |
| 越界的临时单元，下文简称越界单元 | 带标记，序号 < N | N 扩大后覆盖了某个 surge 的序号 |

surge 标记属于单元，记在它的每个 Pod 上，并注明属于哪一层（ServingGroup，还是 Role 实例）。两层各看各的标记：一个 ServingGroup 里有带 Role 层标记的 Pod，不会让这个 ServingGroup 变成临时单元。单元内后来补建或新增的 Pod 继承单元的标记。

预算只用三个计数，都可以直接从对象上数出来。每轮只观察一次；计数从这次观察得出，并随本轮已经决定的动作更新：决定删除的单元记为正在删除，决定创建的单元记为 NotReady。后面的阶段用更新后的计数，否则同一轮里先回收 surge 再替换，会按同一份余量删两次。

| 计数 | 定义 |
| --- | --- |
| `active` | 全部单元数，包含正在删除的 |
| `live` | 没有在删除的单元数 |
| `ready` | `live` 中 Ready 的单元数。包含受保护的、旧版本的和临时的 |

另有三个词在规则里反复用到，定义所在的规则如下。

| 词 | 含义 | 定义 |
| --- | --- | --- |
| 待替换单元 | 这一轮滚动要换掉的 `live` 单元：版本过期且序号 ≥ P 的，以及越界单元 | R11 |
| 正式工作 | 待替换单元里除了序号 ≥ N 的临时单元以外的那些。有正式工作才需要 surge | R25 |
| 灰度停点 | P 大于 0 时的滚动完成：序号 ≥ P 的单元都已是目标版本并 Ready，没有临时单元 | R28 |

## 4. 修订规则

「相对现规范」一列的取值：**保留**（内容不变）、**简化**（结果不变，条件或概念减少）、**改写**（结果变了）、**删除**、**新增**。

**R3 和 R11(b) 是待定条款。** 它们按「不转正」写，本文建议改为转正（D1）。改为转正时，R3 换成「N 覆盖临时单元时清除它的标记，它成为正式单元」，R11(b) 和它的两处例外删掉，其余规则不变。

### 4.1 身份与序号

| 编号 | 规则 | 相对现规范 |
| --- | --- | --- |
| R1 | 正式单元只创建在 `[0, N)` 内，取最低的空闲序号 | 简化。现规范分「原位补建」「补最低洞」「配对补洞」三种情形（§0.6、A.3 第 1、3、4 条），这里合成一条 |
| R2 | 临时单元只创建在序号 ≥ N 的位置，取最低的空闲序号，带 surge 标记，使用目标版本 | 改写。现规范允许 surge 建在范围内的空洞并转为保留组（A.3 第 4 条） |
| R3 | surge 标记在创建时确定，之后不变。临时单元不会成为正式单元。N 扩大后落进 `[0, N)` 的临时单元属于待替换单元（见 R11） | 改写。现规范是进入新范围后保留 UID 并转正（§0.6、A.3 第 1 条） |
| R4 | 只有显式缩容可以让正式单元占用的序号变稀疏 | 保留（§0.6、A.3） |
| R5 | 健康且不需要更新的单元不因整理序号而重建，包括范围外正式单元 | 保留（§0.6、SG-S03） |

R1 加上 R20（缩容只选正式单元）就能导出现规范里几个需要专门说明的结果：

- 替换范围内的旧单元，重建在原序号。它删除后留下的正是最低空闲序号，除非更低处原本就有洞。
- 替换范围外的旧单元，替代容量落在最低的洞（SG-S02、SG-P11）。
- 范围外的目标版本单元健康时，没有人需要创建正式单元，洞保持原样（SG-S03）。

R3 的理由。不转正时，标记是一个不可变的出身记录：带标记的 Pod 最终一定会被删掉，运维看到标记就知道它是临时的。转正需要在运行中改写标记，多 Pod 单元改到一半时身份不确定，实现上还要处理改写失败的重试。

R3 的代价只在 N 于带 surge 的滚动中途扩大时出现：越界单元要重建一次（[6.2](#62-改写的三个场景)），这次重建是 R13 和 R16 的例外（见 R11 后面的说明），U 为 0 时还需要 `N + S` 的容量。完整的比较和社区先例见 D1。

### 4.2 预算

| 编号 | 规则 | 相对现规范 |
| --- | --- | --- |
| R6 | 预算基数取最新 N。U 的百分比向下取整，S 和 P 的百分比向上取整。U 和 S 解析后同时为 0 时拒绝配置，零副本和全部受 partition 保护也不例外。配置被接受之后 N 变化使两者解析为 0 的（例如经 `/scale` 缩容），不做替换，按 R29 报告 | 保留（§0.3、A.2）。后一句是补充，现规范没有写这种情形 |
| R7 | 容量上限：`active ≤ N + S`。已经超出时不再创建任何单元，只清理或等待 | 保留（§0.3） |
| R8 | `minAvailable = max(0, N − U)`<br>`maxScaleDown = max(0, live − minAvailable − notReadyTarget)`<br>`maxHealthyScaleDown = max(0, ready − minAvailable)`<br>其中 `notReadyTarget` 是版本等于目标版本、NotReady、且不属于待替换单元的 `live` 单元数，包含临时单元 | 简化。现规范是 `activeReplicas − minAvailable − unavailableTargetReplicas − inFlightReservations`（API §2.3） |
| R9 | 删除一个 NotReady 的待替换单元，消耗 1 个 `maxScaleDown`。删除一个 Ready 的待替换单元，同时消耗 1 个 `maxScaleDown` 和 1 个 `maxHealthyScaleDown` | 保留（API §2.3） |
| R10 | 每个单元 Ready 后按最新状态重算，不等同批的其他单元 | 保留（§0.7、B.5） |

R8 为什么可以去掉 `inFlightReservations`。现规范定义它是「删除已发出、但还没有体现在 `activeReplicas` 减少或 `unavailableTargetReplicas` 增加上的额度」。一个单元从被删除到替代者 Ready，依次处于三种状态，`live` 和 `notReadyTarget` 已经覆盖了每一种：

| 状态 | 现规范 | 修订规则 |
| --- | --- | --- |
| 旧单元正在删除 | 仍在 `activeReplicas` 中，`inFlightReservations` 加 1 | 不在 `live` 中 |
| 旧单元已消失，替代者还没创建 | `activeReplicas` 减 1 | `live` 减 1 |
| 替代者已创建，NotReady | `unavailableTargetReplicas` 加 1 | `notReadyTarget` 加 1 |

三行里两边的 `maxScaleDown` 相同。现规范 B.2、B.3、B.5 的每一行和 RU-B11 都可以这样对上。

推论，与现规范一致，不单独成条：

- 扩容出来还没 Ready 的单元计入 `notReadyTarget`，不产生删除额度（SG-C01、SG-C15）。
- 已创建但没 Ready 的 surge 同时让 `live` 和 `notReadyTarget` 各加 1，不产生额度（SG-C16）。
- 故障已经让 `ready` 低于 `minAvailable` 时，仍可以在 `maxScaleDown` 内替换 NotReady 的待替换单元，因为这不会再降低 `ready`（SG-S06、SG-S07）。
- 受保护单元的故障会降低 `ready`，因此占用健康删除额度（SG-P09）。这一条有分歧，见 D2。

### 4.3 候选

| 编号 | 规则 | 相对现规范 |
| --- | --- | --- |
| R11 | 待替换单元是满足下面任一条件的 `live` 单元：<br>(a) 版本不等于目标版本，且序号 ≥ P；<br>(b) 带 surge 标记，且序号 < N | (a) 保留；(b) 新增，是 R3 的另一半 |
| R12 | 选择顺序：先 NotReady，后 Ready；同类按序号从高到低。配置了 roleCoordination 的 Role 只按序号从高到低，最高的候选拿不到额度就等待 | 保留（§0.4） |
| R13 | 已经是目标版本但 NotReady 的单元，不因滚动而重建 | 保留（§0.4） |
| R14 | 连续提交新版本时，按最新目标重新判定待替换单元。已发出的删除不撤销；替代者还没创建的，直接用最新版本创建 | 保留（§0.4、SG-C08） |

按 R11，版本过期的临时单元也是待替换单元，和正式单元排在同一个序列里。它序号最高，所以同类中最先被删，删除后按 R25 重新创建一个目标版本的 surge。现规范 SG-C14 的「换 surge」过程因此不再需要单独规定。

R11(b) 是一次身份修复，不是模板更新，所以它有两处例外，需要明确写出：

- **不受 partition 限制。** 越界的临时单元即使序号小于 P 也要替换。重建时按 R15 选版本，所以落在保护区里的会用基线版本。例如 N 从 2 扩到 3、同时 P 从 1 提到 3，原来的 surge `sg-2`（v2，Ready）会被换成 v1。转正时它会保持 v2（R16：提高 P 不回滚已有单元）。
- **不受 R13 限制。** 越界的临时单元即使已经是目标版本、只是 NotReady，也会被重建一次。重建后的单元不带标记，之后适用 R13，不会反复重建。

### 4.4 版本与 partition

| 编号 | 规则 | 相对现规范 |
| --- | --- | --- |
| R15 | 创建一个完整单元时，按它的序号选版本：序号 < P 用基线版本，否则用目标版本。临时单元一律用目标版本。Role 模式下新建 ServingGroup 时，组内每个 Role 实例按该 Role 的 P 同样处理 | 保留（§0.5）。最后一句是补充说明，现规范没有举这个例子 |
| R16 | partition 只限制模板更新。提高 P 不回滚已有单元；P 不阻止显式缩容删除受保护单元 | 保留（§0.5） |
| R17 | 基线版本只在全量完成时推进（R28）：P 为 0，N 大于 0，规模完成，全部单元是目标版本且 Ready，没有临时单元。中途提交的中间版本不会成为基线；P 大于 0 或 N 为 0 时不推进。还没有基线时（ModelServing 新建后从未全量完成过），第一个被持久化的 revision 就是基线 | 保留（§0.5、A.4）。「N 为 0 时不推进」和最后一句是补充说明；最后一句是当前实现的做法 |
| R18 | 局部修复（只补缺失的 Pod，或只重建单元内的一部分）沿用该单元已应用的版本和 worker 布局 | 保留（§0.5、API §6.1） |
| R19 | 需要的历史版本读不到时，等待并报告，不用目标版本代替 | 保留（§0.5） |

R17 只看当前状态，不看旧版本单元是怎么消失的。P 为 0 时，缩容删掉了最后几个旧版本单元、剩下的全是目标版本，基线照样推进：此时没有受保护的槽位，推进后再设置 P，保护的就是现在实际在跑的版本。P 大于 0 时不推进，受保护的槽位之后仍按原基线重建（SG-P03 的故障分支）。

### 4.5 扩缩容

### 4.10 故障恢复与重启

| 编号 | 规则 | 相对现规范 |
| --- | --- | --- |
| R32 | 恢复范围由 `recoveryPolicy` 决定。恢复触发条件、`restartGracePeriodSeconds` 的语义按 API §6 | 保留 |
| R33 | 恢复造成的重建遵守 R15（整单元）和 R18（局部）。恢复删除的单元在消失前不计入 `live` | 保留 |
| R34 | controller 重启后不延续重启前的删除批次，按现存对象和最新 spec 重新判断。健康的幸存成员保留，缺失的成员按 R18 补齐 | 保留（A.4「重启后的删除收敛」、RC-01～04） |

预算、候选和阶段规则（R1～R29）只用集群上可见的信息：surge 标记在 Pod 上，版本在 Pod 标签和 ControllerRevision 上，其余都是每轮现算的计数。故障恢复和重启有三处做不到：

- **外部删除后的恢复范围。** Pod 被外部删除后，按 `recoveryPolicy` 重建整个范围只在 controller 看到了这次删除、之后又没有重启时成立。重启后集群上只剩「缺了一个成员」，与「正在补建」没有区别，按 R34 只补缺失的成员（R32、R34）。
- **删除批次。** 多 Pod 单元的删除只发出了一部分时，「这个单元正在被删除」只有发起删除的进程知道。重启后不续删，幸存的成员保留（R34）。
- **grace 的故障起点。** 现规范要求它跨重启保留（API §6.2），这需要持久化，见 D9。

前两处是现规范本来就有的行为，状态设计 4.7 说明了怎么实现。

### 4.11 InPlace 原地升级

现规范没有覆盖这一部分。下面四条是新增的，原则是让原地升级和重建共用同一套预算和顺序，只在「怎么把一个单元变成目标版本」这一步不同。

| 编号 | 规则 |
| --- | --- |
| R35 | 一个待替换单元满足三个条件时原地更新：`updateMethod` 是 `InPlace`；它从当前版本到目标版本只改了容器镜像；U 大于 0。否则按重建处理。更新方式在计划之前按单元确定。选谁、选几个，仍由 R8、R9、R12 决定 |
| R36 | 原地更新中的单元，从开始打补丁到全部成员在目标镜像上 Ready，视为「目标版本、NotReady」：计入 `notReadyTarget`，不计入 `ready`，不再是候选 |
| R37 | 原地更新中的单元需要重建时（超时、崩溃、成员被删除），整单元和局部重建都直接使用目标版本。目标再次变化或改回原版本时，该单元重新成为普通待替换单元，仍受预算约束 |
| R38 | surge 只为要重建的单元创建：R25 里的「正式工作」只统计按重建处理的待替换单元。待替换单元全部可以原地更新时不创建 surge |

R35 要求 U 大于 0，是因为原地更新期间单元不可用，U 为 0 时没有任何单元可以开始，只能靠 surge，也就是重建。当前实现也是这样处理的。

R38 与当前实现不同：当前实现只要启用了 InPlace 就完全不用 surge，包括实际走重建的变更。见 D6。

### D2 受保护单元的故障是否占用滚动预算

| | 占用（草案，现规范） | 不占用 |
| --- | --- | --- |
| 含义 | U 是对整个 ModelServing 的可用性承诺：滚动不会让 Ready 总数低于 `N − U` | U 只约束滚动区 `[P, N)`：保护区坏了不影响滚动区推进 |
| SG-P09 | sg-0 恢复前不删健康的 sg-2 | 删 sg-2，Ready 从 2 降到 1 |
| 先例 | Deployment、CloneSet、StatefulSet ≤ v1.37.0 | StatefulSet 主干；当前实现（有单测断言） |
| 风险 | 保护区的故障会卡住灰度，需要先修复或调大 U | Ready 总数可能低于 `N − U` |

建议：保留占用。推理服务丢一个 ServingGroup 的代价高，而且 kthena 自己的开发者文档写的是 `N_available ≥ replicas − maxUnavailable`，这是全局承诺。代价是保护区里一个修不好的单元会一直卡住灰度，需要人工处理或调大 U。

如果改为不占用，它是另一种完整的承诺，不能只是「忽略保护区的故障」。需要同时做两件事：把预算基数改成滚动区的单元数，这会改变百分比的解析结果，例如 N=10、P=8、U=25% 时全局解析为 2，按滚动区解析为 0；说明稀疏布局下保护区和滚动区各有几个单元。当前实现两样都没做，见检视意见。

### D4 两套候选顺序是否统一

现状：SG 和独立 Role 是「旧 NotReady 优先，再从高到低」；协调 Role 是严格从高到低，最高候选受阻就等待。

建议：这次不动。严格顺序在低位旧单元故障、预算被它占满时会停住（现规范 SG-S05 的协调对照），只能靠人工处理；但协调模式的 `maxSkew` 和依赖计算都建立在有序前缀上，改顺序要重新推导那一部分。先记为已知的不一致。

### D5 显式缩容是否继续按健康度和 cost 选择

草案保留现状（R20），空洞只来自这一处。另一种做法是缩容恒删最高序号，这样任何时候都是 `[0, N)`，R1、R5、R20、R28 里关于稀疏的内容全部可以删掉，SG-S01～S05、SG-P03 故障分支、SG-P11 需要改写。

建议：保留现状。按健康度选可以避免缩容时删掉健康单元而留下坏的；cost 是 binpack 缩容的输入。代价是规范里要一直带着「范围外正式单元」这一类。

### D6 InPlace 启用时 surge 是否生效

当前实现：只要 `updateMethod` 是 `InPlace` 且 U > 0，`maxSurge` 整体不生效，即使某次变更不满足原地条件、实际走的是重建。用户文档写明了这一点。

草案（R38）：原地更新的单元不用 surge；回退为重建的单元照常用 surge。

建议：采用草案。配置了 S 的用户期望重建时有额外容量，是否生效不应取决于另一个字段。

### D7 `maxSkew` 与旧依赖保留会互相等待

a 依赖 b 时，b 的最后一个旧实例要等 a 没有旧版本才放行，所以 b 的进度最多到 `(Nb − 1)/Nb`；a 的累计可启动数因此最多是 `ceil(((Nb − 1)/Nb + maxSkew) × Na)`。这个数小于 `Na − 1` 时，a 剩下不止一个旧实例，全量末步许可（API §5.1）的条件不成立，两边互等。例如 a 有 8 个、b 有 2 个、`maxSkew=10%`，停在 a 5/8、b 1/2。现规范 B.6 只举了能走通的 8/4/10。

这是规范的缺口，实现照着规范做也会卡住。8/2/10% 的结果是按当前实现的限额函数推演得到的（探针循环调用限额函数，候选过滤是探针里按规则重写的），没有在完整的 reconcile 路径上复现。

逐条依赖边检查 `ceil(((Nb − 1)/Nb + maxSkew) × Na) ≥ Na − 1` 不够。三级链 a→b→c、实例数 8/4/2、`maxSkew=10%` 时，两条边都通过这个检查，仍然停在 a 5/8、b 3/4、c 1/2：`maxSkew` 的基准是所有参与 Role 里最慢的那个，c 被钉在 1/2，a 的上限是 `ceil((0.5 + 0.1) × 8) = 5`。这个例子由提案分析手算得出，没有用探针跑过。

可选的修法有两种：在 admission 对整个协调集合做一次推演，走不到终态的配置拒绝；或者改规则，被旧依赖保留钉住的 Role 不作为 `maxSkew` 的基准。

建议：单独立项处理。两种修法都需要重新推导协调规则，本文没有验证其中任何一种。在此之前，把 8/2 和 8/4/2 两个例子加入必测用例。

### D8 依赖启动顺序是否只约束根 Role

API §5.2 写的是「目标版本先满足依赖 Ready 再启动依赖方」。当前实现和 CRD 注释只让没有被别人依赖的根 Role 等待；三级链 a→b→c 里 b 不等 c。规范的文字和例子都只有两级，没有覆盖这一点。

建议：在规范里明确写出是哪一种，再决定改规范还是改实现。现规范的文字没有把约束限定在根 Role 上，所以选择「只约束根 Role」是语义变更，需要一条三级链的启动过程作为例子。

### D9 故障起点是否必须跨重启保留

API §6.2 要求同一次持续故障的首次观察时间跨 controller 重启和主备切换保留。这是修订规则里唯一需要持久化的时间信息；当前实现没有持久化，重启后重新计满一个 grace。

建议：保留这条要求，把起点写在 Pod 注解上。它同时让 grace 到期判断可以改成每轮现算，不再需要进程内的定时任务（见状态设计）。落地时还要定两个细节：升级前就处于故障态、没有注解的 Pod 从哪个时刻起算（现规范只说了不能用创建时间）；Pod 恢复 Ready 后清除注解失败、随后再次故障时，如何不沿用旧起点。

运行：

下面的命令在 `model/` 目录里运行，前面加 `PYTHONDONTWRITEBYTECODE=1` 可以不留下 `__pycache__`。

- `uv run --no-project python scenarios.py`：汇总表和各项检查。
- `uv run --no-project python scenarios.py --tables SG-C03 SG-C03+promote`：单个场景的过程。`+promote` 是把 R3 换成「转正并清除标记」的变体。模型还有第三种变体「转正但保留标记」，只用在 D1 的对比里。
- `uv run --no-project python scenarios.py --fuzz 20000`：草案和转正变体各跑三种模式、三个种子的随机测试。

模型检查的内容：

- **每轮两条不变量**：`active` 不超过 `max(本轮开始时的 active, N + S)`；`ready` 不低于 `min(本轮开始时的 ready, N − U)`。
- **场景**：每个场景的创建和删除次数。转正变体必须与现规范的次数相同；修订规则只允许在 SG-C03、SG-P08、SG-P10 上不同。
- **基础预算矩阵**：15 种组合的终态版本、终态序号、启动顺序。草案和转正变体各跑一遍。
- **随机序列**：每条序列是 1～8 次 spec 变更（N、U、S、P、目标版本、deletion cost），变更之间穿插随机次数的 reconcile、删除完成和 Ready。三种模式各跑 3 个种子、每个种子 2 万条，草案和转正变体各 18 万条：
  - 全量：最后把 P 置 0。检查收敛、没有残留的 surge、全部是目标版本并 Ready、基线已推进；序列里没有缩容时终态是 `[0, N)`。
  - 灰度：保留随机的 P。检查没有残留的 surge、序号 ≥ P 的单元都是目标版本、没有非缩容造成的空洞。
  - 故障：过程中随机出现永远不 Ready 的版本和卡住的删除，结束前解除。检查过程中两条不变量始终成立，解除后能收敛。

模型的范围和限制：

- 只模拟一个预算范围（一组 ServingGroup，或一个 ServingGroup 内一种 Role 的实例）。不模拟 Role 层与 SG 层的嵌套、roleCoordination、故障恢复和 InPlace。
- 环境只有三种事件：删除完成、单元变 Ready、spec 变更。每轮的观察和执行是原子的，没有缓存滞后、API 部分成功、并发的 Ready 回落。
- 转正变体只替换了 R3，其余规则与修订规则相同。它不是现规范的完整实现；与现规范的对照靠的是手工数出的次数和逐场景的过程比对。「转正但保留标记」变体只跑了 D1 表里的三个情形，没有跑随机测试。
- 初始状态里基线等于目标版本，N 至少是 1，U 和 S 不会同时为 0。R17 里「还没有基线」和 R29 里「U 和 S 解析为 0」两种情形模型没有覆盖。
- 随机测试不包含「永远放不下的单元」。D1 表里不转正时不收敛的两种情形是单独构造的，随机测试发现不了它们，不变量检查也不会报错，因为容量和可用性都没有被突破。
- 模型开发过程中，随机测试和提案分析各发现过一处规则缺口，都已修正：补正式单元也要受容量上限约束（R7、R23 第 2 步）；判断 surge 超额不计正在删除的单元（R26）。
