### 0. 一页结论

**方向。** ServingGroup 和 Role 实例保持逻辑概念，一个 controller，Pod 的 owner 不变。改三件事：

1. 回调只入队；每一轮的决定是「对象快照加一份很小的账本」的函数（第 6、7 节）。
2. Pod 集合里读不出来的两个事实（建成过、删除范围已提交）记在 `ModelServing.status.units` 里，用区间编码；
   每个事实只有这一个来源（第 4、5 节）。
3. 部署上保证同一时刻只有一个 controller 在动作（第 12.3 节）。

**四个考量。**

| 考量 | 方案的回答 | 证据和它的限度 |
| --- | --- | --- |
| reconcile 效率 | 一轮只读缓存；直读有四种、都有界，协调滚动的直读先沿用基线；创建和删除并行分批；稳态不再空写 status。不依赖结构的几项可以先做（P0） | 基线【Kind】：滚动一个组 31–57 个请求，其中读 24–49 个；100 个组的滚动 330 秒，把限速从 5 提到 50 之后 65 秒。方案一侧是【推演】：读降到每个组个位数；status 写的次数与基线持平到数倍（第 8 节） |
| 管理复杂度 | 没有新的对象种类，没有第二个 controller，Pod 不换 owner。新增 status 里一个字段、9 条协议规则，另有屏障、降级、分类表和 3 条部署前提（第 9 节逐项列出） | 对照表。它没有的东西也列了：按组的对象、`kubectl` 直接可见、kthena 不在时清理一个组 |
| 状态一致性 | 基线上会影响决定的 20 处来源收成四处持久来源：spec、ControllerRevision、Pod、账本。从 P2 起、账本可写时，内存里只剩「只能推迟」的四样 | 第 4 节。有三格取决于裁决（槽位、新一代的身份、surge），照实标出。基线的后果【Kind，一次】：升级 controller 时两个进程并存约 11 秒，之后滚动卡住 5 分钟，直到再次重启 |
| status 的规模 | 序号连续时 `units` 约 0.1 KB（124 字节，其中 45 字节是所属对象的 UID），与组数和实例数无关；序号稀疏时与空洞数成正比，每个空洞约 6 字节；在途时随在途的范围数增长。有字节上限，放不下的位置退回「只补缺」 | 【计算】`evidence/status-size/`：1000 个实例，稳态 124 B，binpack 缩掉一半之后的稳态 1.6 KB，最大的在途状态 3.1 KB。逐实例的账本是 62 KB，声明成键控列表时 `managedFields` 再加 112 KB【Kind】 |

### 2. 目标、边界、不做的

**目标**：同一份集群状态，不论 controller 什么时候重启、换主，发出的动作相同；用户给的四个考量各有可检验的回答。

**边界**（沿用前序任务已定的）：

| # | 约束 | 出处 |
| --- | --- | --- |
| C1 | 不引入 ServingGroup CR；一个 controller；Pod 的 owner 是 ModelServing | 011 |
| C2 | 不用 Pod finalizer | 008；LWS 维护者同样否定 |
| C3 | Pod 的名字和序号不变；`spec` 不增减字段。`status` 可以新增字段，要批准 | 007 |
| C4 | 身份与 #2126 对齐：子对象上的实例 ID 标签，取等比较 | 011 |
| C5 | 契约 2.13、2.14 的语义：建成按 Role 实例判断；删除范围的提交先于第一个 DELETE、重启后可读；记录的零值不引起任何删除 | 契约 API §6.1、§6.2 |

**不做的**：把记录放在成员 Pod 上（011 的三个反例）；每个组一个记录对象；逐实例的账本（规模）；
改滚动和扩缩的规则（除非第 13 节另行批准）。

### 3. 五条原则

| # | 原则 | 落在哪 |
| --- | --- | --- |
| 一 | **每个事实恰好一个来源。** 能从对象上读出来的不另存；读不出来的只存一处 | 第 4 节 |
| 二 | **决定是本轮快照的函数，内存只能推迟动作。** 清空内存之后最终发出的动作相同 | 第 4.2、7 节。从 P2 起、账本可写时成立 |
| 三 | **先记后做。** 不可撤销的一步之前，先用一次带 resourceVersion 的 status 写把它记下 | 第 5.2 节 W1–W4 |
| 四 | **账本只写直读确认过的事实；没写账本的轮次，动手前复核账本。** 缓存用来计划，不用来给账本作证 | 第 5.2 节 F1、F2 |
| 五 | **记录的大小在序号连续的稳态下与单元数无关，并且有字节上限；零值安全。** 记录丢了、放不下、写不进去，都退回「只补缺」，不会引起删除 | 第 5.2 节 Z、K；5.4、5.5 |

先例和条文【静态，`subagents/community-research.md`】：

- 有的：API conventions 的「Sequencing operations」预料到「先在 status 里确认、再动作」，并要求 status 是输入时用 resourceVersion
  前置条件、冲突就让本轮失败（kubernetes#105199）；Job 的 `uncountedTerminatedPods` 是「只记在途、先写后做、有上限」；
  `completedIndexes` 是区间编码（它不截断，大小靠 spec 校验限制）；写后屏障是 KEP-5647。
- 没有的，共六处：二维（组 × 实例）区间的规范化；「建成过」放在父对象的 status 里；`draining` 只记位置不记身份
  （Job 记 UID，JobSet 记逐位置的计数器，LWS 记 UID 的摘要）；按多 Pod 的单元分批；同一轮只写一次并且先写后做；
  放不下时截断。另外「旧二进制整对象写回时抹掉新字段」没有查到条文。

| 持久输入 | `status.currentRevision`、`updateRevision`、`collisionCount` | status，被读回 | 不变。连同 `units`，这四个是 status 里**被读回当输入**的全部字段 |
| 只推迟 | 故障起点（grace 计时） | `graceMap` 加每个故障 Pod 一个睡眠的 goroutine，goroutine 拿的是旧 spec | 内存，按 Pod UID 记；用延迟入队，不起 goroutine；到期时按最新 spec 重算。中途恢复过 Ready 要从 Pod 上读出来（Ready 条件的转换时间晚于起点就重新起算），因为 worker 看不到中间的事件 |
| 只推迟 | 本进程的写已被接受、缓存还没看到 | 创建后立刻写 `datastore` | 写后屏障，管 status 的写和 Pod 的 CREATE（7.3） |
| 只推迟 | 初始同步是否做完 | `initialSync` 加启动时把每个 Pod 当新增事件重放 | 不需要：第一轮直接从缓存分类 |
| 输出 | 汇总计数、conditions | 由 `datastore` 算出 | 由同一份快照算出。见 4.3 |
| 另一份实现 | 驱逐 webhook 自己判断「单元是否就绪」，并有自己的 ConfigMap 记录 | `webhook/eviction_handler.go` | 判断改用同一个分类函数。ConfigMap 记录不在本方案范围内 |
| 集群 | 有没有 PodGroup CRD；PodGroup、Service 是否存在 | 内存缓存；直连 API | informer 缓存 |

#### 4.2 内存里剩下的

从 P2 起、账本可写时，内存里是四样，都只能推迟：故障起点；写后屏障；ControllerRevision 的解码缓存；「上次报告的阶段」。
最后一样只用来发 `RoleCreating`、`RoleRunning` 这类事件（上游把它们当对外行为，有 e2e 断言），不参与决定。
另有两样只影响报告和兜底的直读，不改变决定：「上次自己写的账本非空」（5.5 用它发现账本被抹）；T1、T2 的起点
（对象有 `deletionTimestamp` 时取它，取不到的记在内存，重启后重新起算）。

**两种情形下内存会改变决定**：P1 期间（账本接口用内存实现）；P2 之后账本写不进去而降级时（5.5）。
这时「丢失是整范围恢复还是只补」「重启后已提交的删除做不做完」取决于进程内存，与 `main` 今天相同。

#### 4.3 status 里不是「只是输出」的字段

`observedGeneration`、`replicas`、`labelSelector`、`CoordinatedRoleRolloutBlocked` 的 reason 被别的组件当输入读：
校验 webhook、LWS controller、HPA（经 scale 子资源）【静态】。方案不改这些读者，要求它们是同一份快照的函数，与账本在同一次写里提交。
两处没有定、要在 P1 的差异清单里逐项定：

- **计数的口径**：清空中的、未建成的、有成员在终止中的组各算不算进 `replicas`、`availableReplicas`。默认逐项沿用基线。
- **`observedGeneration` 追平的时机**：先写后做之后，它在动作之前就追平，webhook 和 LWS controller 据此保守等待的窗口变短。

### 5. status 账本

#### 5.1 形状

```yaml
status:
  units:                       # 缺失 = 没有任何位置建成，没有任何提交
    uid: 6f1c2a9e-3b4d-4c5e-8f70-123456789abc   # 所属 ModelServing 的 metadata.uid
    established:               # 建成过的位置
    - roles: [decode]          # 组区间和实例区间都相同的 Role 合成一条
      groups: "0-79"
      indices: "0"
    - roles: [prefill]
      groups: "0-2,4-79"
      indices: "0"
    draining:                  # 已提交删除、还没清空的范围
    - scope: ServingGroup      # 整组
      groups: "90-99"
    - scope: Role              # 单个 Role 实例
      roles: [prefill]
      groups: "3"
      indices: "0"
```

- **规范形式唯一**：区间升序、相邻合并、单点不写成区间；每个 Role 下实例区间相同的组归成一个矩形，矩形相同的 Role 合成一条，
  `roles` 按名字的字节序；各条按 `roles`、再按第一个组序号排；`draining` 里整组范围在前；整组范围吸收同组的 Role 范围。
  同一个集合只有一种编码，「计划出来的和现有的相同就不写」可以直接比较。
- **列表都声明成原子列表**。`managedFields` 因此是常数【Kind：约 0.25 KB；键控列表是每项约 112 字节】。
- 不含 Pod 的名字和 UID、时间、revision。
- 账本带所属对象的 UID（`uid`，45 字节；账本为空时整个字段不写）；与 `metadata.uid` 不同时当零值。它挡的是「status 被整份搬到另一个同名对象上」。

#### 5.2 规则

第三列里，【模型】是在模型里去掉这条规则得到的反例，【推演】是没有进模型的。

| # | 规则 | 去掉它会怎样 |
| --- | --- | --- |
| Z | **零值安全。** 位置不在 `established` 里就是未建成：缺成员只补缺，绝不因此删除。账本缺失、被抹、放不下，都落到这一条 | 【模型】「只记例外」的编码在账本被抹之后把没建完的单元当成丢失，整范围删除 |
| W1 | **提交先于删除。** 对一个范围的任何整体删除（丢失或故障的范围恢复、滚动替换、缩容、surge 回收）先用一次 status 写把范围记进 `draining`、把其中的位置移出 `established`，写成功之后才发第一个 DELETE。范围种类按写入那一刻的策略定，之后不变。**被提交的位置不要求已建成** | 【模型】整组范围删到一半中断、策略又改成 `None`，剩下的被补齐而不是删完 |
| W2 | **清空先于创建。** `draining` 的范围里一个子对象都没有了，才从 `draining` 移除；移除的写成功之后才在这些位置上创建，可以在同一轮里。子对象是一张固定的清单，按范围的种类分。Role 范围：该实例的 Pod（含终止中的）和它的两个内置 headless Service（与 entry 同名的一个，和 `<entry>-discovery`）。整组范围：组内全部 Pod、各实例的 Service、该组的 PodGroup。PodGroup 只属于整组范围，清空一个 Role 实例不删它、也不等它。它们由 controller 按 owner 和位置标签直接删，带 UID 前置条件，不依赖 plugin 的钩子成功；plugin 自建的其他种类不算 | 【模型】新建的 Pod 被当成旧范围的成员删掉 |
| W3 | **一轮至多一次账本写，在本轮的 DELETE 和「清空之后的 CREATE」之前。** 写带 resourceVersion，不先 GET、不就地重试。409：本轮什么都不做，直接重新入队。别的失败（超时、5xx）：依赖这次账本变化的动作不做，不依赖它的在 F2 通过之后照做。写完核对返回的对象里 `units` 等于发出去的，不等就判定「账本写不进去」（5.5） | 一轮一次写和 409 在模型里；没有「去掉它」的变体，别的失败不在模型里 |
| W4 | **回收当轮写。** 位置不再被保留、也没有子对象了，当轮从 `established` 移除。这是一次账本变化，不等别的变化捎带 | 【推演，提案分析 A5】缩容后 Pod 全丢、以后又扩回，会被判成丢失，`ServingGroupRecreate` 下重建整组 |
| F1 | **账本只写直读确认过的事实。** 要改账本的一轮，对涉及的范围直读一次，在读到的结果上重新判断：记建成，要读到成员齐全、都不在终止中；因丢失而提交，要读到确有成员不存在；清空，要读到范围里什么子对象都没有。直读必须是一致读（类型化 client 不带 resourceVersion 的 GET 或 LIST），不能是 lister，也不能带 `resourceVersion=0` | 【模型】去掉清空前的：一个 controller 时范围就会被过早清空，旧成员被并入新一代。去掉建成前的：有第二个行动者时，没齐全过的单元被记成建成。去掉丢失前的：有第二个行动者时，没有缺成员的单元被提交清空 |
| F2 | **没写账本而要动手的轮次，先直读一次 ModelServing。** resourceVersion 与计划时的不同就放弃本轮。CREATE 和 DELETE 都算动手 | 【模型】有第二个行动者时健康的新 Pod 被删。只管 DELETE、别的规则都在时，没有新的违反，但 5.3 那三件拦不住的事变多：建进清空中范围的 Pod 是三倍，提交之前被补上的近两倍 |
| L | **丢失的判定。** 位置在 `established` 里、被保留、不在 `draining` 里，并且**有成员不存在**。`None`：只补；`RoleRecreate`：提交这个实例；`ServingGroupRecreate`：提交整组。提交放不下时按规则 K 退回只补缺。还在终止中的成员占着名字，不算丢失，等它消失。不被保留的位置缺成员不算丢失 | 没有进模型的变体。「终止中不算」与基线一致 |
| K | **上限按字节。** 整个 `units` 的编码（含 UID，以及裁决之后加进来的集合）不超过 8 KB（暂定）。在途的记录优先（`draining`；选了的话还有 `creating`、`surge`）：它们放不下时，按确定的次序（从最大的组序号起）丢掉 `established` 的记录腾地方。`established` 用剩下的：放不下时不再记入新的位置，并且先查容量、放不下就不做建成前的直读。没记进去的和被丢掉的位置按未建成处理（Z），报 condition。任何会让 `established` 变大的移除（W4 的回收、把一个位置从区间中间移出）放不下时，同样丢掉它所在的整条记录。即使丢光 `established` 也放不下时：因丢失而要提交的位置不等，把它移出 `established`（必要时丢掉它所在的整条记录，这只会变小），按未建成只补缺；因故障、滚动、缩容而要提交的等前面的范围清空，这时清不掉的范围已经在报 T2 的 condition（第 6 节第 1 行）。只做清空的写只会变小，永远放得进；选了 `creating` 之后，放行创建的记录写不进去时那一批创建等着，成员全没了的位置的补缺也在其中（例如只有 entry 的 Role 实例丢了它的 Pod）：这种情形下「丢失不等待」不成立，怎样取舍没有定 | 没有进模型，也没有脚本。上一稿是「`draining` 至多占一半、满了就等」，复查指出清不掉的范围会在 4 KB 处堵住别的丢失（复查 N1），改成现在这样。改后的写法经过一次窄范围的核对，没有引出错删；核对指出的三处衔接（W4 的移除、`creating`、L 的例外）补进来之后没有再看 |

四点说明：

- **F1 的范围**是被改动的那几个位置，不是整个 ModelServing。一轮里要改很多位置时，换成一次按 ModelServing 的 LIST。
  预算（`maxUnavailable`）仍按缓存算，F1 不复核它。
- **哪些规则挡的是什么。** 一个 controller、缓存只前进时，够用的最小集是 Z、W1–W4、F1 里清空的那一种，加写后屏障（7.3）【模型】。
  F1 的另外两种和 F2 不只是防第二个行动者：新启动的进程首次 LIST 可以由 apiserver 的缓存应答，Pod 的快照可能比账本旧
  （提案分析 A1 的场景只有一个进程）。所以它们不是可有可无的保险。
- **提交写自动校验了 spec**：spec 一变 resourceVersion 就变，写会 409。「按写入那一刻的策略」不需要另外的机制。
  这是账本放在 ModelServing 自己身上才有的性质。
- **`None` 之下照常记建成**。`None` 自己用不到它，代价是每个位置一次直读和分摊的一次写；换来的是不为它单开一种模式，
  以及从 `None` 切到别的策略时记录已经在。

#### 5.3 位置的一生，和模型的结果

```text
            补缺                 F1 直读：成员齐全                 W1 提交（一次写）
（无记录）─────────►  创建中  ──────────────────►  established  ──────────────────►  draining
    ▲                                   记建成（一次写）                                    │ 删范围里的子对象
    │                                                                                       ▼ F1 直读：范围里什么都没有
    └───────────────────────────────  W2 清空（一次写），同一轮里接着创建  ◄───────────────┘
```

模型（`model/README.md`）把「计划和它的直读」「status 的写到达」「每个 Pod 请求到达」拆成各自的一步，任意两步之间可以插入别的事。结论：

| 规则集 | 一个 controller | 加一个缓存冻结、还在动作的行动者 |
| --- | --- | --- |
| 全部规则 | 11 个场景没有违反：三种策略、策略切换、缩容再扩回、账本被抹 | 没有违反。下面三件拦不住的事只计数 |
| 去掉 W1、W2、Z 中任一条 | 有反例 | — |
| 去掉 F1 的清空前直读 | 有反例（整组策略） | 有反例 |
| 去掉 F1 的建成前、丢失前直读 | 没有违反（模型里新进程的缓存不会比账本旧） | 有反例 |
| 去掉 F2 | 有屏障时没有违反 | 有反例 |

全部规则之下仍然会发生的三件事，根源相同：CREATE 没有前置条件，拦不住一个早先计划好、晚到的 CREATE。

| 事情 | 后果 | 什么时候 |
| --- | --- | --- |
| 迟到的补缺 | 补上了之后才丢失的成员，本该整范围恢复的单元只被补齐 | 一个 controller：只在「`None` 改成别的策略、丢失、已计划的补缺」三者交错时。第二个行动者：它没发完的 CREATE 都可能这样 |
| 提交之前被补上 | 直读看到成员不存在、提交的写到达之前，迟到的 CREATE 把它补上了：一个此刻不缺成员的单元被整范围恢复。方向是策略要的方向 | 只在有第二个行动者时 |
| 建进清空中范围的 Pod | 随范围一起被删。契约的「不吸纳同名新 UID」在这种情形下不成立 | 只在有第二个行动者时 |

#### 5.4 大小【计算】

`units` 的字节数，紧凑 JSON，不含 `managedFields`，含 45 字节的 UID（账本为空时没有）。完整的表在 `evidence/status-size/ledger-size.md`。

| 形状 | 状态 | 逐实例全量 | 本方案 | 加上 `creating` |
| --- | --- | --- | --- | --- |
| 100 个实例（50 组 × 2） | 稳态，序号连续 | 6.1 KB | 123 B | 123 B |
| 1000 个实例（500 组 × 2） | 稳态，序号连续 | 62.3 KB | 124 B | 124 B |
| 2000 个实例（1000 组 × 2） | 稳态，序号连续 | 124.8 KB | 124 B | 124 B |
| 1000 个实例 | 稳态，序号十个里缺一个 | 62.3 KB | 0.5 KB | 0.5 KB |
| 1000 个实例 | **稳态，binpack 缩掉一半之后**（随机留一半） | 62.4 KB | 1.6 KB | 1.6 KB |
| 2000 个实例 | 同上 | 125.9 KB | 3.5 KB | 3.5 KB |
| 1000 个实例 | 一成的组在清空、一成在创建，序号随机 | 61.7 KB | 0.9 KB | 1.1 KB |
| 1000 个实例 | 首次创建，还没有位置建成 | 59.3 KB | 2 B | 137 B |
| 1000 个实例 | 每隔一个组建成 | 60.8 KB | 1.1 KB | 2.1 KB |
| 1000 个实例（10 组 × 100） | 按 Role 滚动，一成的实例在清空，位置随机 | 61.0 KB | 3.1 KB | 3.1 KB |

- **序号连续的稳态与规模无关。序号稀疏的稳态与空洞数成正比**，每个空洞约 6 字节。binpack 缩容留下的空洞不是暂态。
  按 8 KB 的上限，随机留一半的形状大约在留下 2000 多个组时触及：超出的位置长期按未建成处理，丢了成员只补。
- 在途时随**在途的范围数**和序号的零散程度增长，不随总数增长。
- **片段数相同，字节可以差八倍**：512 个片段是一条记录时 2.1 KB，是 256 条两个片段的 `draining` 记录时 16.8 KB。所以上限按字节定。
- 最坏的形状是「每个组的实例集合都不同而且都是碎的」，大小与位置数成正比，每个位置约 2.5–5 字节【推演，提案分析 1.6】。
  Role 一级按删除代价缩容会造成它。规则 K 为它而设。
- `creating` 一列假设在途的位置都是同一次写放行的、共用一个令牌，是下端；分多次放行时每多一个令牌多一条记录。
- `surge` 没有量；它是一个组区间，量级与 `draining` 的一条整组范围相同。

**写的次数和字节。**

| | 基线【Kind】 | 本方案【推演】 | 逐实例账本【推演】 |
| --- | --- | --- | --- |
| 一次滚动的 status 写次数 | 10、30、100 个组：15、33–50、34–48 次，即每组 0.3–1.7 次。**跟着轮数走，不跟着组数走** | 每批组三次账本变化（提交、清空、建成）。100 个组、每批 10 个：同一批合并时约 30 次，完全不合并时约 300 次；另加只改计数的写，可以限速合并。**与基线持平到数倍** | 次数相同 |

#### 5.5 零值、升级、回退、CRD

| 情形 | 发生什么 | 依据 |
| --- | --- | --- |
| 首次升级 | 账本为空，全部位置未建成。第一轮（直读确认后）把齐全的位置记为建成：每个 ModelServing 一次写，集中在启动之后。这之前的丢失只补缺（契约允许） | 【推演】 |
| CRD 没有先升级 | apiserver 接受写、裁掉 `units`、只给一个 warning。W3 的核对发现返回的对象里没有 `units`：判定「账本写不进去」，依赖账本变化的动作不做；退回内存账本（行为同阶段 P1），报 condition 和事件。启动时另查一次 CRD 的 schema。以后每次要写账本时照常尝试，写得进去就恢复 | 【Kind】`field-probe.md` A2 |
| 写被校验拒绝 | 同上。CRD 里的长度上限不能小于规则 K 的上限 | 【推演】 |
| 发现账本被别人抹掉 | 上次自己写的非空、现在读到空：报事件和 condition。按零值继续 | 【推演，提案分析 A4】 |
| 不认识账本的二进制写了一次 status | `units` 被抹掉，回到零值：只补缺。被打断的已提交删除不再继续，剩下的 Pod 被补齐 | 【Kind】`field-probe.md` D、E |
| 它什么时候写 | `main`：计数或 condition 变了就写；全部更新、全部可用、没有 partition 时，每处理一个 Pod 事件都写（第 1 节第 4 行）。**这是一道失效保证**：没有人维护过的记录多半已经被抹掉，不会被新版本拿去删东西。它的条件要写全：P0 修掉空写之后，只剩「计数或 condition 变了才写」；设了 partition 的对象本来就没有后一半 | 【Kind】【静态】 |
| 它没有写过 status | `units` 原样留着，可能陈旧。两种坏结果：位置在 `established`、而它的 Pod 被换过又没建完，会被判成丢失（F1 把它限制在确有成员不存在的情形）；一条已提交、还没发出 DELETE 的范围，旧二进制什么都不用做，会原样留到再次升级，然后被执行 | 【Kind】`field-probe.md` C；【推演】 |
| 新旧同时在动作 | 12.3 要求排除。排除不了时，旧的随时抹掉账本，已提交的范围会被打断，旧的还会往清空中的范围里建 Pod；带记录的方案在这里都不安全，本方案退化成「只补缺」 | 【推演】 |

为了让上面的失效保证不依赖空写，本线自己的、不认识账本的版本（P0、P1）启动后第一轮对每个 ModelServing 写一次 status。
回退到 `main` 时没有这一条，靠的是 `main` 自己的写。

契约里有一处要决策的张力：§6.1 说带范围标记的成员「在任何空窗之后都必须完成」，§6.2 说「记录丢失之后、重新建立之前的缺员只补缺」。
上表依据的是后一句（决策 [D2](#d2)）。

#### 5.6 别的编码为什么不用

| 编码 | 稳态大小 | 不用的原因 |
| --- | --- | --- |
| 逐实例的全量账本（011 的路径 B） | 每个实例约 61 字节 | 规模。协议最简单；实例数长期在几十以内时它其实最稳 |
| 只记例外（没记的算已建成） | 约 20 字节 | 不是零值安全的【模型】；扩容出来的新位置在写下例外之前就是「已建成、没有 Pod」 |
| 每个位置一个代数计数器（JobSet 的做法） | 每个位置几字节，线性 | 规模。它的优点是计数器同时就是身份，提交和「认出旧的一代」是同一个事实 |
| ModelServing 的注解；ConfigMap | 同本方案 | 不会被不认识它的版本抹掉，所以会陈旧，要另造失效机制；ConfigMap 还失去「提交与 spec 同一个版本」。上游有 ConfigMap 的树内先例（驱逐 webhook），目标是上游而上游坚持不动 status 时，它是退路 |
| 不加任何记录，只做结构重构加 #2126 | 0 | 不满足契约 2.13、2.14；controller 不在时的丢失仍然只补 |

### 6. 位置的分类和反应

每一轮先算**保留集合**：按 spec、现有的位置（有子对象的，或在账本里的）和缩容的选择规则，定出保留哪些位置。
它是计划函数的第一步，在分类之前。保留的序号可以是稀疏的（binpack 缩容之后）。然后对每个位置按下表判断，从上往下第一条适用的生效。

ModelServing 自己在删除中（带 `deletionTimestamp`）时：不创建、不提交，删除交给垃圾回收器。

| # | 条件 | 状态 | 反应 |
| --- | --- | --- | --- |
| | **清空中的范围** | | |
| 1 | 在 `draining`，范围里还有子对象 | 清空中 | 范围里有故障成员时先只删它们，它们消失之后删其余（基线的两步，决策 [D8](#d8)）；直接删清单里其余的子对象（Role 范围：它的 Service；整组范围：各实例的 Service 和 PodGroup，见 W2）；调 plugin 的删除钩子。等了超过 T1 直读剩下的对象（丢了删除事件的兜底）；超过 T2 报 condition，不放行创建 |
| 2 | 在 `draining`，直读确认没有子对象 | 已清空 | 移出 `draining`（W2），同一轮里按下面的行继续 |
| | **不保留的位置** | | |
| 3 | 有子对象。Role 一级不保留的位置只看它的 Pod 和 Service；整组不保留时加上 PodGroup | 多余 | 提交（W1）。整组不保留时提交整组 |
| 4 | 没有子对象 | — | 移出 `established`（W4） |
| | **保留的位置** | | |
| 5 | 布局读不出来（它的 revision 找不到） | 未知 | 不记建成、不补、不因丢失或故障提交、不替换；报告。没有自动的出口，只有显式的缩容能动它（与基线一致） |
| 6 | 有故障成员，策略会恢复（不是 `None`，grace 不是 `-1`），已过 grace | 故障 | 提交对应范围 |
| 7 | 不是目标 revision（含成员 revision 不一致），预算允许 | 待替换 | 提交；能原地更新的走原地更新，不经过账本 |
| 8 | 不在 `established`，成员不全 | 创建中 | 补不存在的成员；终止中的等它消失 |
| 9 | 不在 `established`，直读确认齐全、都不在终止中 | — | 记建成（F1） |
| 10 | 在 `established`，直读确认有成员不存在 | 丢失 | 按规则 L；提交放不下时按规则 K 退回只补缺 |
| 11 | 在 `established`，没有成员不存在，有成员在终止中 | 等待 | 无。超过 T2 报 condition |
| 12 | 在 `established`，齐全 | 运行 | 无。是否 Ready 只影响计数 |

- **故障是叠加的判断，不是一种互斥的状态。** 有故障成员而第 6 行不适用时（`None`、grace 为 `-1`、还没到期），不因故障提交，
  继续往下判断：照常替换（契约：`None` 不关闭正常的模板滚动）、照常补缺、照常按丢失恢复、照常记建成。还没到期的另外安排到期时重排。
- 第 3、7 行不看是否建成：创建一直失败的旧版本单元也能被替换【提案分析 A6】。
- T1、T2 没有定值。量级上 T1 是 Pod 的终止宽限期加几十秒，T2 是几分钟；T2 到了之后是否放行创建是决策 [D9](#d9)。
- 预算怎样算（哪些单元算不可用、surge、partition）属于计划函数，本方案不改它的规则。

### 7. 一轮 reconcile

#### 7.1 结构

```text
observe   informer 缓存：ModelServing；它的全部 Pod（按 owner 的索引，一次）；Service、PodGroup、ControllerRevision
retain    纯函数：保留集合
classify  一次遍历把 Pod 分到位置上；每个位置按第 6 节分类
plan      纯函数，不做 I/O：新的账本、动作列表、汇总 status
confirm   要改账本：对涉及的范围直读，在读到的结果上重算这几个位置（F1）
persist   status 与现有的不同：一次 UpdateStatus（W3）。只改输出字段的写可以限速合并，账本的写不限速
act       没写账本而有动作：先直读 ModelServing（F2）。然后并行分批发请求
requeue   有等待（grace、对象消失、屏障）就延迟入队
```

回调只入队，key 是 ModelServing。回调里不读写任何生命周期状态，不发 API 请求，不调 plugin 钩子；
`OnPodReady` 这类钩子改在 worker 里按快照调用。它们的调用次数和失败时的语义是决策 [D15](#d15)。

#### 7.2 直读的清单

| # | 什么时候 | 读什么 | 频率 |
| --- | --- | --- | --- |
| 1 | 要改账本（F1） | 涉及的范围里的 Pod（清空时加 PodGroup、Service） | 每个位置的一生约 3 次小的读：建成、提交、清空 |
| 2 | 有动作而没写账本（F2） | ModelServing | 这样的轮次 1 次 |
| 3 | 清空中的范围等了超过 T1 | 范围里剩下的对象 | 只在等待超时时 |
| 4 | CREATE 得到 AlreadyExists；删一个孤儿 Service 之前 | 那个 Pod（核对 owner、位置、revision，不符就报错重排，不当成功）；那个位置的 Pod | 只在撞名、有孤儿时。基线今天这样做 |
| — | 协调滚动的一轮 | 现有的直读先保留：基线在每个协调轮 LIST 一次这个 ModelServing 的全部 Pod，**不是有界的** | 同基线。量过、分析过之后再定 |

前四种有界。协调滚动是基线里直读最密的部分，本稿没有逐行分析。

#### 7.3 写后屏障

本进程写过 status、或建过 Pod 之后，缓存里出现这次写之前不计划这个 ModelServing。它只推迟，不改变动作，重启后不需要。
DELETE 不设屏障：拿不到删除之后的版本，重发的 DELETE 有 UID 前置条件。
这是上游四个内置 workload controller 从 1.36 起默认开启的机制（KEP-5647）【静态，社区调研 2.3】。
kthena 用的 client-go v0.35.3 还没有上游的库，自己实现逐对象的比较，接口留成与上游相同的形状。三处要做对：
没追上时按错误返回、由队列重排，否则可能永远不再处理；空操作的写（返回的 resourceVersion 没变）不设屏障；
ModelServing 的更新事件在 spec 没变时现在不入队，屏障要靠它或靠定时重排来唤醒。

#### 7.4 动作

- 创建和删除在一轮内并行分批（ReplicaSet 的 slow-start）。批内失败只影响各自的位置。PodGroup 先于它的 Pod。
  批次的排序决定配额不足时能凑齐几个完整的组，是决策 [D16](#d16)。
- DELETE 一律带 UID 前置条件，UID 取自缓存；PodGroup 和内置的 Service 同样带。
- Pod 事件入队时可以加一个短的合并延迟（Job controller 是 1 秒），减少轮数。作为可调项，默认值量过再定。

### 8. 效率：基线和方案

基线是【Kind】实测（`evidence/kind-baseline/RESULTS.md`）。方案一栏是按第 7 节数出来的【推演】，是区间的下端，实现之后要在同一套脚本上量。
「组」在这里是测量用的形状：2 个位置、3 个 Pod。

| 项 | 基线 | 方案（预期） |
| --- | --- | --- |
| 没有事件 | 没有请求 | 没有请求 |
| 稳态下一个 Pod 就绪事件 | 回调里 3 次 `GET controllerrevisions`，加 worker 一轮 2 次 LIST 和 1 次内容相同的 `UpdateStatus` | 0 个请求 |
| 创建：每个 Pod 的请求数 | 2.9–7.7 | 约 1.7 起：1 次 CREATE，加每个位置 1 次建成前的读（每组 2 次），加分摊的 status 写 |
| 滚动：每个组的请求数 | 31–57，其中读 24–49 | 约 12 起：3 次 DELETE、3 次 CREATE、每个位置约 3 次小的读（按整组范围时每组 3 次），加分摊的 status 写 |
| 缩容：每个被删的组 | 13–19 | 约 5 起：3 次 DELETE、1–2 次读，加分摊的 status 写 |
| status 写 | 稳态每轮一次空写；滚动 15–50 次（10–100 个组；100 个组是 34–48 次） | 不变就不写；100 个组的滚动约 30–300 次账本的写，另加限速合并的计数写（5.4） |
| 一轮的 CPU（1000 个 Pod） | 没有量 | 2–5 毫秒【推演，提案分析 4.3】 |
| 单个大 ModelServing | 一个 key 一个 worker | 不变。并行靠一轮内的分批 |

没有计入方案一栏的：每个 Pod 就绪翻转引出的计数写；事件；PodGroup 和 plugin 的 Service（基线也没有量）；
选了 `creating` 之后创建之前的那次写；协调滚动的直读。

- **限流是前提。** 默认的 5 QPS 之下，并行分批没有作用，请求在限流器里排队；先记后做多出来的写和读也要排队。
- **先记后做对完成时间的影响**：每个被替换的范围在关键路径上多两次写和两次小的读，各一个 API 往返。限流不是瓶颈时，
  相对 Pod 的终止和启动可以忽略；前提是 409 之后直接重排，不走指数退避。别的写者（改 spec 的用户、经 scale 子资源的 HPA）造成的 409 只推迟这一轮。

### 10. 身份

- 结构本身去掉了 #1957 的成因：迟到的删除**事件**不再触发恢复，恢复只看快照和账本；每个 DELETE 带 UID 前置条件。
- 实例 ID 标签（#2126）与账本是两个维度。模型里的协议没有用 ID。标签仍然有用：给 Service 和 PodGroup 分代；
  让混合了两代成员的位置认得出。
- **采用标签之后必须回答**【提案分析 A3】：去掉 `datastore` 之后，一个位置的新一代在它的 Pod 被缓存看到之前，ID 记在哪。
  不回答的话，CREATE 部分成功后的下一轮会给同一个实例再取一个 ID。如果 P1 开始时 #2126 已经合入，这个问题在 P1 就要回答，不是 P3。

  | 做法 | 内容 | 代价 |
  | --- | --- | --- |
  | 账本里记在途的创建（建议） | 第三个集合 `creating`：W2 清空、或给全新的位置放行创建的那一次写，同时写下这批位置和它们的令牌；建成时移除。令牌是一个随机的短串，同一次写放行的位置共用一个，所以也能区间化（5.4 的最后一列）。它同时回答「清空之后槽位记在哪」（4.1） | 多一个集合；首次创建和每次扩容在 CREATE 之前多一次写；零值多一个含义（没有放行）。**没有进模型** |
  | 创建前直读 | 缓存里看不到任何成员的位置，创建前直读该位置，读到就沿用 | 多一种直读；两个进程各取各的 ID 时挡不住；槽位的问题没有解决 |

- 采用标签之后还要有一条规则：同一个位置上成员的实例 ID 不一致时，按「不是目标 revision」处理，经提交替换。
  依据在 Pod 上，但删除仍然经过账本。没有进模型。
- 提案分析建议把身份排在账本之前（P0、P3、P1、P2）。没有照此改次序，理由是模型里不带 ID 的协议在所查范围内成立；
  这是决策 [D17](#d17)。

### 15. 没有验证的和残余风险

1. **方案没有实现。** 第 8 节的数字、12.1 的行为都是推演。
2. **模型很小**：最多 4 个 Pod、2 个位置；没有滚动、surge、协调滚动、原地更新、故障和 grace、预算、PodGroup 和 Service；
   第二个行动者最多计划 2 轮；W3、W4、L 没有「去掉它」的变体；K、`creating`、`surge` 不在模型里。W2 对 PodGroup 和 Service 的活性没有任何证据。
3. **协调滚动、原地更新、LWS 路径、驱逐 webhook 没有逐行分析。** 协调滚动是基线里直读最密、状态最多的部分；
   原地更新不经过账本，两个进程可以各自开始一次原地更新；原地更新超时的入口怎样接到新的 grace 计时上没有看。P1 开始之前要先做这部分的走读。
4. **第二个行动者的残余**：5.3 的三件事；预算按缓存算，Pod 缓存停住的行动者可以多提交一个范围；旧版本中途接手一个做到一半的清空，
   会留下新旧两代混在一起、以后又被记成建成的位置【推演，提案分析 A4】。`main` 今天也会留下同样的半截实例；差别是 P2 承诺了「做完」而这里做不到。
5. **不是本 controller 维护、而又非空的账本**：不认识账本的版本没写过 status（5.5）；有 `modelservings/status` 权限的人或工具写回一份旧对象。
   `draining` 没有有效性检查，见到就删。UID 只挡「搬到另一个对象」这一种。
6. **上游**：维护者对 status 里的账本和对水平触发的重构都没有表过态；#2126 还开着、没有人评审。
7. **基线测量的局限**：每个规模一次；没有 Volcano、没有 plugin、没有协调滚动；并存的场景一次、QPS 不是默认值；
   限流等待只记到超过 50 毫秒的，超过 1 秒的可能重计；启动重放和 plugin 的读没有量；请求数里含同一个进程里别的 controller 的少量请求和事件的写。
8. **`managedFields`、裁剪、空操作写**是在 v1.37.0 上看到的行为，没有查别的版本。
