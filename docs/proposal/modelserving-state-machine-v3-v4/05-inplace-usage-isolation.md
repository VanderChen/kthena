# 原地更新：在使用上隔离

## 0. 文档信息

| 项 | 内容 |
| --- | --- |
| 用途 | 原地更新是一种很特殊的模式。这里不给它做一台更细的子状态机，而是限制它能出现的组合和时机，让核心的大部分状态走不到它；剩下的交叉收成几个固定的接口点。对 [v3](03-v3-state-machine.md) 和 [v4](04-v4-servinggroup-cr.md) 都适用 |
| 基线 | v2 的 [07](../modelserving-rollout-final/07-core-state-machine.md) B 部分：6.2 的对照表、第 7 节的 15 条约束、8.4 的三处没有写到的地方 |
| 状态 | 逐条给建议，不替维护者决定。会改变已发布说明或已批准行为的条目单独标出 |
| 依据 | 「走读」指读代码和文档得出。没有运行任何测试 |
| 编号 | I1 到 I5 是草稿里的五条候选限制。H 开头是提案分析补充的条目，在任务目录 `subagents/proposal-analysis-v4.md` 第 6 节里编号是 R1 到 R12，这里换成 H 以免和 005 的规则编号（R15、R35、R38 等）相混。v2 的不变量也叫 I1 到 I14，本文不引用它们 |

## 1. 做法

07 把原地更新从核心里拆出来之后，B 部分仍然有 15 条约束，其中不少是和别的功能的交叉：和 surge，和恢复策略，和协调，和「滚动途中改配置」。隔离的意思是三件事。

1. **减少组合。**能在配置上排除的组合，用 webhook 排除。
2. **把运行时的回退变成配置上的事实。**今天「写了 `InPlace` 却悄悄走了重建」有好几种原因，都是每一轮才判断的。能在创建时判断的，就在创建时拒绝。
3. **剩下的交叉走固定的接口点。**核心只通过第 4 节的几个接口点看见原地更新，不知道它内部怎样续补、怎样记重启基准。

`InPlace` 在 v1.1.0 的发布说明里标为 Alpha，注明 API 和行为可能变（走读，`docs/kthena/blog/release-v1.1.0/index.md:142`、`354`）。收窄它在承诺的范围之内。但下面有几种组合是用户指南里明写支持的，逐条说明。

## 2. 对每一条限制都成立的两件事

### 2.1 只拦新引入的

今天 ModelServing 的校验 webhook 对每次 CREATE 和 UPDATE 把全部静态检查重新跑一遍，不看这次改了什么（走读，`webhook/validator.go:119-148`）。它的失败策略是 `Fail`，不含 `/status` 和 `/scale` 两个子资源。

所以，一条新的限制如果照现有的写法加进静态检查，每一个已经在用这种组合的 ModelServing，从升级那一刻起：

| 对主资源的更新 | 后果 |
| --- | --- |
| autoscaler 改副本数。它 PATCH 的是主资源，不是 `/scale`（走读，`pkg/autoscaler/controller/autoscale_controller.go:199-201`、`493-494`） | 被拒绝，自动伸缩停止 |
| 用户改一个标签或注解 | 被拒绝 |
| 前台删除时垃圾回收摘 `foregroundDeletion` | 被拒绝，对象删不掉（推断） |
| `kubectl scale`、HPA、controller 写 `status` | 不受影响 |

**规则：新的限制只在 CREATE 时，或者相关字段在这次更新里从不违反变成违反时拒绝。**旧对象已经违反、相关字段没有变的，放行并返回一条 warning。CREATE 不受这条保护：存量对象的清单不能原样用来重新创建，要写进升级说明。`deletionTimestamp` 非空时放行。这个文件里已经有按新旧对象比较的校验可以照着写（走读，`webhook/role_coordination_validator.go:214-286`）。CRD 里的 CEL 规则要到 Kubernetes 1.30 才默认有这种行为（推断），项目支持 1.28，所以放在 webhook 里。

### 2.2 webhook 删不掉状态

放行存量对象，意味着 controller 仍然会遇到被禁止的组合；升级时已经带着未完成注解的 Pod 也还在。状态机要求每个状态都有反应，「很少走到」不等于「走不到」。

**规则：每条限制都有第二半。**controller 里一个纯函数，把被禁止的组合规范化成允许的一种，下面叫**有效更新方式**。存量对象经过它之后和新对象走同一条路。规范化的结果如果是「当作 `Recreate`」，这些用户升级之后的下一次滚动会从原地变成重建，要写进升级说明。

| # | 限制 | 手段 | 建议 |
| --- | --- | --- | --- |

| I2 | 滚动进行中不允许改 `updateMethod` | webhook | **不采纳**。换成「作废」的规则（H3） |

| I5 | 超期的成员一律当作故障的成员交给恢复 | 规则的合并，不涉及 webhook | **采纳** |

### 3.1 I1：`InPlace` 时不配 surge

| 项 | 内容 |
| --- | --- |
| 今天 | 接受，行为有定义。webhook 里没有任何关于 `updateMethod` 的检查。`InPlace`、plugin 都支持、U 大于 0 时走原地，期望数不加 S；U 为 0 时与 `Recreate` 完全相同，照常用 surge（走读，`ipu.go:104-124`，`msc.go:819-823`）。测试 `TestSurgeDisabledWhileUpdatingInPlace` |
| 文档 | 写明支持。用户指南：「`maxSurge` only applies when every outdated resource is recreated」；同一节建议不能接受中断的用户在 `InPlace` 下设 `maxUnavailable: 0` 和 `maxSurge: 1`（走读，`multi-node-inference.md:433`、`438`） |
| 去掉什么 | 07 第 7 节第 5 条；6.2 里 A7 一行的「正式工作里要有按重建处理的」；待决项 O4 和行为规范的 D6 不再需要回答。连带：`maxSurge` 为 0 时已有的校验要求 U 大于 0，所以第 1 条里的「U 大于 0」和第 15 条里「U 为 0 时不走原地」这两个全局条件也没有了 |
| 用户失去什么 | 文档里推荐的那种写法要改成 `Recreate`；今天两者行为相同，没有功能损失。要改的文字：用户指南 `multi-node-inference.md:432`、`433`、`438`，API 注释里 `maxUnavailable` 可以解析为 0 的条件。`RoleRollingUpdate` 下「这个 Role 原地、那个 Role 用 surge 重建」的混合用法没有替代，因为 `updateMethod` 是整个 ModelServing 的。plugin 不支持时今天会回退成带 surge 的重建，之后只能显式写 `Recreate` |
| 措辞 | 按配置的值写，不按解析的结果：没有设、`0` 或 `0%`。百分比解析成几随副本数变。只检查当前生效的那一层 |
| 规范化 | 存量对象配了 `InPlace` 又配了 surge：有效更新方式按今天的代码，U 大于 0 是原地、不用 surge，U 为 0 是重建。行为不变 |
| 去不掉的 | 滚动途中把 `updateMethod` 改成 `InPlace`、同时把 `maxSurge` 改成 0 是合法的，这时已经建出来的 surge 还在。所以要 H10 |

它把今天的行为（原地时不用 surge）从运行时的判断变成配置上的事实。**需要维护者明确同意放弃 R38 和 D6 的方向**（回退为重建的单元照常用 surge）。

一处已有的同类问题会更常见：`maxUnavailable` 和 `maxSurge` 不能同时解析为 0 的检查是按当前副本数算的（走读，`validator.go:245-250`）。`maxUnavailable` 写成百分比、`maxSurge` 为 0 时，autoscaler 把副本数调小到百分比向下取整为 0 的那一刻，它的 PATCH 会被拒绝（推断）。I1 把所有 `InPlace` 的用户都放进了 `maxSurge` 为 0 这一格。所以这条已有的检查也要改成只拦新引入的：`maxUnavailable` 和 `maxSurge` 的配置没有变、只是副本数变了的更新不拒绝。

### 3.2 I2：滚动中不许改 `updateMethod`

不采纳，理由有三条。

1. **webhook 看不到「进行中」。**它只看得到 ModelServing 对象，「进行中」只能从 `status` 读。更新作废之后被 partition 盖住、成员还没完成的单元不在现有的滚动信号里：`status` 说没有滚动，集群里却有未完成的注解。
2. **放行和动手之间有间隔。**webhook 放行的那一刻看 `status`，controller 可能下一刻才开始打补丁。
3. **用户失去一条写在文档里的退路。**用户指南：「You can switch back to `updateMethod: Recreate` at any time」（走读，`multi-node-inference.md:435`）。原地更新卡住时，今天可以改回 `Recreate` 让滚动把它重建。partition 大于 0 的灰度停点可能持续几天，这期间这个字段都改不了。

所以 07 的 8.4 那三行无论如何要在状态机里有定义。换成一条规则（H3）：

> **有效更新方式不是原地时，带未完成注解的单元算作废：版本记为过期，是待替换单元，按重建处理，走预算。**

这就是用户指南那句话。8.4 的第 1、2 行由此只有一种行为；第 3 行由 I1 加 H10 覆盖。

**它和 04 的字面、和当前代码都不一样，要批准。**分两种单元：

| 改回 `Recreate` 时单元的情形 | 04 的字面 | 当前代码 | H3 |
| --- | --- | --- | --- |
| 只打了一部分补丁 | 仍是原地更新中，接着续补 | 直接删除整个单元，不看预算和 partition（走读，`ipu.go:509-517`、`758-763`） | 作废，按重建处理，走预算 |
| 全部打上补丁，还没就绪 | 仍是原地更新中，等完成或超期 | 成员都在目标镜像上就绪时照常完成；在那之前它是未就绪的旧单元，被替换选中后删除，占额度 | 作废，按重建处理，走预算。就绪之前被替换选中的结果与当前代码相同；差别是不再等它就绪后算作完成 |

### 3.3 I3：不和 roleCoordination 同用

| 项 | 内容 |
| --- | --- |
| 今天 | 支持，有专门的代码和测试。部分打了补丁的 Role 算作「已经用掉一次目标版本的启动」，因为原地更新在完成之前保留旧的 revision 标签（走读，`controller/coordinated_round.go:120-139`）。测试：`coordinated_inplace_regression_test.go` 的 6 个，e2e `TestModelServingCoordinatedInPlaceProgress` |
| 用户失去什么 | prefill 和 decode 分离、用协调滚动的部署不能原地换镜像。这正是 Pod 最贵、只改镜像最常见的场景。roleCoordination 创建之后不可变，这些用户只能改 `updateMethod` |

这条限制不是必需的。在 v2 的模型里，原地更新中的单元就是「目标版本、未就绪」（R36）。只要分类把这个结论交给协调的候选函数，协调就不需要知道原地更新。当前代码里那两处特殊处理的来源是协调直接读 revision 标签。第 4 节的接口点「记账」做在分类里，这个交叉自己就没有了。

如果实施时协调的改造排在原地更新之后，可以把它当作阶段性的限制：只拦新的，有效更新方式定为重建，在发布说明里写明。那样存量的协调加原地的对象升级之后会从原地变成重建，是一处行为变化，要批准。

### 3.4 I4：不和 `None` 或 grace `-1` 同用

| 项 | 内容 |
| --- | --- |
| 今天 | 支持。恢复不生效时成员「在目标镜像上运行」就算完成，不看期间的崩溃；超期不删除，没打上补丁的成员继续续补（走读，`msc.go:2242-2245`，`ipu.go:640-645`、`735-737`）。有单测和 e2e |
| 文档 | 两处都写了。用户指南：「`None` or `restartGracePeriodSeconds: -1` leaves the Pods alone, so the update stays pending until the image becomes Ready」。API 注释把「misses an in-place update deadline」列在 `-1` 的含义里（走读，`multi-node-inference.md:434`，`servinggroup_types.go:119-121`） |
| 用户失去什么 | 五条里代价最大的。选 `None` 的人要的是 controller 不要动我的 Pod；选原地更新的人要的是保住节点位置、已下载的权重和缓存。这是同一批人 |

可以不禁止，只留一个输入（H5）。草稿要去掉的两条特例是「完成不看计划外重启」和「超期只报告、一直续补」。

- 第二条并进核心：续补不看期限；超期之后未完成的成员成为重启故障一类的故障成员（I5）。`None` 和 `-1` 下核心对重启故障的反应本来就是只报告。
- 第一条剩下一个布尔量：恢复是否生效。它由核心给出，原地更新这一层只读它。

### 3.5 I5：超期一律当作故障的成员

| 项 | 内容 |
| --- | --- |
| 今天 | 恢复生效时，超期的单元里从没打上补丁的成员直接删除，不等 grace；带未完成注解的成员等 grace（走读，`ipu.go:726-755`） |
| 文档 | 用户指南只写了「unfinished Pods are handled like failed Pods according to `recoveryPolicy` … (after `restartGracePeriodSeconds`)」，没有提不等 grace 的那一类。合并之后的行为反而和文档一致 |
| 去掉什么 | 07 的 6.3 里 A9 第二张表的第二行；04 的时机表的第四行 |
| 用户失去什么 | grace 是正数时，没打上补丁的成员多等一个 grace。grace 默认是 0，没有差别。进度期限最短 60 秒、默认 1800 秒，相比之下一个 grace 可以忽略 |

要补两处定义：

- 没打上补丁的成员从 Pod 上看是健康的，它成为故障的成员靠的是所在单元的事实（更新已超期）。分类的次序因此是先单元、后成员，和核心里「成员是输入、单元是输出」的方向相反，要写明。
- 哪些成员算：带未完成注解的，和没有注解、标签也不是目的 revision 的。按目的 revision 补建出来的成员不算，否则重建出来的成员立刻又是故障的。

「故障的成员」按重启故障计时（等 grace），不按终态（不等）。D13 之后用户指南里「like failed Pods」这句话本身有歧义，要改。

### 3.6 补充的条目

| # | 内容 | 依据 | 去掉什么 |
| --- | --- | --- | --- |
| H8 | plugin 不支持原地更新时拒绝 `InPlace` | 今天是每轮判断、全部回退（走读，`ipu.go:109-117`）。plugin 的配置创建之后不可变（`webhook/plugin_validation.go:28-50`），是创建时就能判断的事实 | 07 第 7 节第 1、15 条里的全局条件「plugin 链支持原地更新」。和 I1 一起，全局的回退条件一条不剩。它把「写了 `InPlace` 却悄悄不生效」变成一个明确的错误。影响面：`headless-service` 不支持原地更新，而多节点的部署基本都声明它，这些对象今天写 `InPlace` 实际走的是重建。plugin 链建不出来是运行时的错误，不是配置上的事实，应当归到「等待」，不归到「不支持」 |
| H9 | `restartPolicy` 必须是 `Always` | 今天是逐单元判断、回退（`ipu.go:276-290`） | 第 1 条里的重启策略条件。模板是静态的，创建和每次改模板时都能检查 |
| H10 | 临时单元一律按重建处理 | 见 I1 的「去不掉的」。当前代码对版本过期的临时单元会按原地更新打补丁 | 8.4 第 3 行剩下的一半 |
| H11 | 原地更新中的单元出现成员缺失，这次更新作废 | 07 第 7 节第 10 条：补成员用哪个版本有三条优先级 | 少一条优先级：不存在「给一个半新半旧的单元补成员」。代价落在 `None` 的用户上：更新期间被人删了一个 Pod，整个单元会被滚动重建，而不是只补这一个 |
| H12 | 作废的单元一律是待替换单元，不看 partition，按重建处理，走预算 | 07 第 7 节第 8 条的四种去向是 B 部分里分支最多的一处 | 四种变一种。放弃的是：被 partition 盖住、已经在原来的目的镜像上就绪的单元「保持原样」；被 partition 盖住、没完成的单元「等进度期限」。前者是让一个标签和实际镜像不一致的单元长期运行 |

没有列进来的：只允许一种滚动单位用 `InPlace`。两种都有代码和测试，选不出该留哪一种。

「只改了镜像」是每次变更才知道的事，不可能在配置上限制，所以「进入」必须一直是逐单元的函数。

## 4. 接口点

核心和原地更新之间只有下面五个接口点，加一个只读的输入。

| # | 接口点 | 方向 | 内容 |
| --- | --- | --- | --- |
| 1 | 进入 | 核心问 | 替换（A8）选中一个单元时，纯函数给出三个结果之一：打补丁、删除、等待。有成员在终止、或者历史版本读不出来时是等待；等待的单元照样占名额。有效更新方式的规范化、「临时单元按重建」「有终态成员按重建」都在这个函数里 |
| 2 | 记账 | 原地告诉核心 | 原地更新中的单元在核心眼里是「目标版本、未就绪」。做在分类里，预算、要不要建 surge、协调、基线推进都不用另写分支 |
| 3 | 成功 | 原地告诉核心 | 全部成员完成，翻转标签，单元回到就绪 |
| 4 | 超期 | 原地告诉核心 | 未完成的成员成为故障的成员，之后是核心的事（I5） |
| 5 | 作废 | 原地告诉核心 | 这次更新不再有效：目标又变了；有效更新方式不再是原地；最后一个带注解的 Pod 没有了。单元回到核心，版本记为过期 |
| — | 恢复是否生效 | 核心给原地 | 只读的布尔量。「完成」看不看计划外重启由它决定 |

续补、重启基准、注解的格式都在原地更新这一层内部，不是接口点。

草稿只列了四个接口点，缺「作废」，「进入」少一个结果（等待）。

**和恢复在同一轮里的次序。**

- v3：范围里有持有的 Pod，或者有本轮要提交的故障成员时，本轮不给这个范围打补丁。v2 让路里和原地更新有关的三句（04 的 4.2 第 4 步）收成这一句。
- v4：实例在 Draining，或者组已经失败，就不打补丁。这是对象上的事实。

**v4 的一个选项。**账本可以多一个值「更新中」，带目的 revision 和开始时间。意图不再只在 Pod 上，「最后一个带注解的 Pod 没有了，意图就丢了」（D12 的收窄）不再发生；进入时的那一次 status 写同时是提交点。代价是账本多一个值，进入多一次写。重启基准仍然留在 Pod 注解里。没有采用，列为选项。

## 5. 采纳之后还剩什么

按第 3 节的建议（I1、I5、H3、H8、H10、H12 采纳；I2、I4 不采纳；I3 不作为长期限制），07 第 7 节的 15 条里：
