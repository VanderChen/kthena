# ModelServing 状态机：v3（确定的）和 v4（ServingGroup 作为 CR）

005 的终稿把 ModelServing 的状态机梳理成了 [v2](../modelserving-rollout-final/README.md)。它还有一个问题：同一份观察可以有不同的反应。最典型的是单元里缺一个成员，可能是还没创建完，只该补建；也可能是成员丢了，该把整个范围删除重建。区分两者的事实不在对象上。

本目录给出两份设计。

| 版本 | 含义 |
| --- | --- |
| v1 | 当前实现，`volcano-sh/kthena` `main` @ `79c455ef` |
| v2 | 005 的理想状态机：[04](../modelserving-rollout-final/04-state-machine.md)、[06](../modelserving-rollout-final/06-state-table.md)、[07](../modelserving-rollout-final/07-core-state-machine.md)，分支 `feat/005-modelserving-rollout-design-review` @ `549581a8` |
| v3 | ServingGroup 仍是逻辑概念。不增减 CRD 字段，不改 Pod 的名字和序号。通过取舍得到确定的状态机 |
| v4 | ServingGroup 变成 CR，去掉组序号。评估它能把设计简化到什么程度 |

全部是文档，没有修改 controller 代码，没有在 Kind 上运行任何东西。规则用一个可执行的小模型穷举过，模型和输出在任务目录 `issues/features/007-modelserving-dfa-state-machine-v3-v4-IP/model/` 下。**推荐项都没有经过维护者裁定**，要裁定的事集中在[下面](#要裁定的取舍)。

## 结论

**1. v2 不确定的根源是单元没有自己的对象。**「这个范围丢过成员」「这个范围正在重建」是范围一级的事实，而范围只是一组 Pod 上的标签。这样的事实要么放在内存里，重启就丢；要么拆开写在每个 Pod 上，不能原子完成。v2 两样都用了：外部删除的记录在内存里，恢复标记写在范围内的每个 Pod 上。

**2. v3 不增加对象，把事实缩小到一个 Pod 带得动的大小。**缺失只有一个含义：创建。丢失的证据是被删的那个 Pod 自己：需要保护的 Pod 带一个 finalizer，被任何人删除之后停在原地，直到 controller 处理完。删除者的那一次 DELETE 同时写下了证据。范围一级不存任何东西。v2 的恢复标记、个数 n、M1 到 M7 七条规则、两项会改变动作的内存、三个丢失窗口和待决项 O9 都不再需要。

**3. v3 的代价是运维上的，只落在范围多于一个 Pod 的地方。**controller 不在时，受保护的 Pod 被删之后会卡在终止中；controller 在场时，它也要等到范围里其余的 Pod 被删才消失；卸载、回退和升级窗口都要按步骤来。范围只有一个 Pod 的配置（例如 `RoleRecreate` 下没有 worker 的 Role）不带 finalizer，状态机和每个 Pod 的代价都不变。

**4. v4 对状态机能简化，对系统不能。**恢复变成一个对象上的一次写；组一级没有 surge 标记、转正、回收和序号空洞。但多一个 CRD、一个 controller、一套两者之间的约定和一次迁移；partition 的语义要改；Role 一级和原地更新没有受益。

**5. 锁是状态放错地方的结果。**只要回调和 worker 都要读写生命周期状态，就得有东西把它们串起来。v3、v4 里回调只入队，状态在对象上，每个写带前置条件，所以没有按资源的锁。没有解决的并发问题也列出来了：计划和写之间别的对象变了；两个进程同时在写；预算是对多个对象求和。

**6. 原地更新不引入不确定，引入的是状态和边的数量。**能用 webhook 排除的组合不多：五条候选限制里建议采纳两条，其中只有一条是 webhook 的限制。更有效的是把运行时的回退变成配置上的事实，把剩下的交叉收成五个接口点。

## 四个版本的对照

| | v1 | v2 | v3 | v4 |
| --- | --- | --- | --- | --- |
| 缺一个成员时怎样决定 | 删除事件有没有送到本进程；内存里的单元状态 | 内存里的外部删除记录；Pod 上的恢复标记和个数 | 范围里有没有带着保护 finalizer 被删的 Pod | 账本里这个实例是不是已建成 |
| 丢失的证据 | 一次事件 | 内存记录，随后写到每个 Pod 上 | 被删的 Pod 自己 | 一个对象的 `status` |
| 提交点 | 没有 | 范围内每个 Pod 各一次 PATCH | 删除者的那一次 DELETE | 一次带 resourceVersion 的 status 写 |
| 证据产生的时刻 | 事件到达时 | controller 决定恢复时 | 删除发生时 | 实例建成时 |
| controller 不在时发生的删除 | 取决于时刻：回来时 Pod 还在终止，可能整范围重建；已经消失，只补一个 | 只补一个（O9） | 受保护的 Pod：整范围重建 | 建成之后：整范围重建。建成之前：只补一个 |
| 会改变动作的内存 | datastore 的单元状态等六项 | 两项加一个子项 | 没有 | 没有 |
| 只影响时机的内存 | — | 在途的写，故障起点 | 同左 | 同左 |
| 按资源的锁 | 没有。回调和 worker 交错；在这个结构上补交错，会走到按 ModelServing 的互斥锁（01 的 2.3） | 没有 | 没有 | 没有 |
| 重启之后 | 重放事件重建内存，结果取决于时刻 | 已经开始的做完；三个窗口里退化 | 与不重启相同 | 与不重启相同，前提是重启后读到的 `status` 是新的 |
| 恢复时每个 Pod 多的写 | — | 1 次 PATCH（标记） | 1 次 PATCH（放行） | 0。每个实例固定 3 次 status 写 |
| 计划内删除每个 Pod 多的写 | — | 0 | 受保护的 Pod 1 次 PATCH | 0。每批删除 1 次 status 写 |
| 新增的卡住方式 | — | — | controller 不在时受保护的 Pod 卡在终止中；controller 在场时，被删的 Pod 要等范围里其余的 Pod 被删 | 采用组的 finalizer 时组卡住；本文选前台级联，没有 |
| 组的序号 | 有 | 有 | 有 | 没有 |
| surge 标记、转正、回收 | 有 | 有 | 有 | 组一级没有 |
| partition | 按序号 | 按序号 | 按序号 | 组一级按数量，Role 一级按序号 |
| 队列的 key | ModelServing | ModelServing | ModelServing | ModelServing 和 ServingGroup 各一个 |
| CRD | — | 不变 | 不变 | 新增 ServingGroup |
| Pod 的名字 | — | 不变 | 不变 | 前缀变成随机后缀的组名 |
| 滚动和扩缩容的规则 | — | 基线 | 与 v2 相同。恢复和缩容的衔接有一处差别（03 第 8 节 L8） | 组一级重写，Role 一级与 v2 相同 |

**T9 怎么看。**两者不是先后关系，是两种代价的选择。

- 不想动 API、不想迁移：v3。它的全部风险在 finalizer 的运维上。
- 愿意加一个 CRD：v4 的恢复比 v3 更干净，没有 Pod finalizer，没有卡住的 Pod。它的风险在迁移、两个 controller 之间的滞后，以及一组还没有模型的规则。
- 两者都要：不建议先 v3 的 finalizer 再 v4。那是两次迁移。这时 v3 应当改选 T1 里的注解账本，它和 v4 是同一个机制。
- 用户指出「组的序号没有意义、副本是等价的」，这一点 v4 满足，v3 不满足。v3 保留序号是因为不改 Pod 名字是给定的前提。

## 没有做的和没有验证的

- 没有改 controller 代码、现有测试、CRD、runner 的契约和用例。因此没有做 Kind 验证，任务状态保持进行中。
- 没有修改 005 的文档。v3、v4 只引用它们。
- 模型跑过的形状是 1×2×2、2×1×2、1×2×1（组数 × 每组的实例数 × 每个实例的 Pod 数），最多 4 个 Pod，不含滚动、原地更新、落后的快照和第二个 controller 实例。v3 的滚动规则沿用 v2，由 005 的参考模型覆盖；两者的衔接是推演。
- v4 里组一级的滚动、按数量的 partition、缓存新旧不一时的两条规则（直读、代际）都没有模型。
- 关于 Kubernetes 行为的结论（各种删除方式下 `deletionGracePeriodSeconds` 的取值、kubelet 写终态的时机、三种级联删除、Helm 对 `crds/` 的处理）来自源码和文档的走读，没有在集群上验证。
- Volcano 对被 finalizer 留住的 `Succeeded` Pod 的计数对 PodGroup 的实际影响没有验证。
- runner 契约 2.7 的用例没有逐条对照。
