## 1. 判据

01 把「不确定」说成「看到的东西相同，选出的动作可以不同」。只要求「动作是快照的函数」是不够的：把 v2 的外部删除记录直接删掉、缺失一律只补建，也是快照的函数，但它丢了语义；「看见终止中的 Pod 就删其余的」也是快照的函数，但它会误删。判据还要说函数忠于什么。下面八条采用提案分析给出的写法，用 J 编号，避免和 005 的决定 D1 到 D15 混淆。

| # | 名字 | 内容 |
| --- | --- | --- |
| J1 | 函数 | 每一轮要发的写的集合 `W = δ(spec, S, now)`。`S` 是本轮的对象快照。`now` 只和从 `S` 里读出的时间戳比较，不和内存里的时间比较 |
| J2 | 只能扣留 | 实际发出的写是 `W` 的子集。内存可以让 `W` 里的写晚发，不能让 `W` 之外的写发出，不能改写的内容。扣留有上界，上界与重启次数无关。不满足上界的内存项逐条列为豁免，并写明后果 |
| J3 | 证据持久 | 设计给两类环境事件规定了不同的反应时，从事件发生到反应完成为止，`S` 里一直有区分它们的事实，它的存续不依赖 controller 在场。做不到的，显式合并成同一个反应，并列入「分不清的情形」 |
| J4 | 提交原子，前缀封闭 | 每个不可撤销的决定，提交点是一个对象上的一次写。一轮写序列的任何前缀之后，状态仍被分类函数归到恰好一个状态；它的反应是接着做还是按最新事实重新决定，由规则写明，不由停下的时刻决定 |
| J5 | 陈旧安全 | 每个写带前置条件：UID；结果取决于 finalizer 或注解现值的写再带 resourceVersion。被写的对象在计划之后变了，写就被拒绝。别的对象或 `spec` 在计划之后变了，一个写挡不住；这类情形逐条列为豁免 |
| J6 | 环境 | kubelet、用户、别的 controller 是环境。本 controller 的另一个实例（默认不开选主）和另一个版本（升级、回退期间）也是环境，J5 要对它们成立 |
| J7 | 进展 | 写明公平性假设：kubelet 最终停止容器并确认；别人的 finalizer 最终被摘掉；API 最终成功。假设成立时，每个不是目标的状态都有一个可以发出的写。假设不成立时停在哪个状态、对外报告什么，逐条写明 |
| J8 | 完备 | 每个 Pod、每个范围、每个单元恰好一个状态；每个状态在每种配置下恰好一个反应 |

「动作」只指会反馈回快照的写：对 Pod、Service、PodGroup 的写，和 `status.currentRevision`。事件和日志不算，重启后不补发事件不违反判据。

按这八条重新看 01 的清单：

| 项 | 违反哪一条 | 说明 |
| --- | --- | --- |
| N1 外部删除记录 | J2 | 记录在内存里，丢了之后发出的是另一个写 |
| N1 的另一半、N3：恢复标记和个数 n | J3 | 它在对象上，`δ` 是函数。问题是不忠实：「个数少于 n」对应两段不同的历史 |
| N2 不算外部删除的集合 | J2 | 同一个终止中的 Pod，新旧 leader 给出不同的写 |
| N4 范围种类 | 不违反 | M3、M7 是确定的规则。它是语义上的选择，见 [4.2](#42-恢复的范围已经开始的按原范围做完) |
| N5 故障起点 | J2 的上界 | 只影响时机，但上界与重启次数有关。列为豁免，见 [4.6](#46-故障起点保留列为豁免) |
| N6 在途的写 | 主体不违反 | 前提是每个写带够前置条件（J5）。子项「上一轮 DELETE 确定失败的记录用于让路」违反 J2，见 [4.4](#44-让路换成两条从快照得出的规则) |
| N7、N8 | J8 | 规则没写 |

v2 自己没有声称是 DFA。04 的不变量 I9 写的是「新 leader 与旧 leader 的差别只来自四项内存信息」。准确的说法是：v2 的 `δ` 多了一个不在对象上的输入，其中两项（N1、N2）加一个子项会改变输出；另有两处（N3，和 N1 里标记的那一半）在对象上但不忠实。

## 2. 两种手段

消除一处不确定只有两种办法。

- **外化**：把起区分作用的事实放到对象上，并且让它和事件同时产生。事后由 controller 补写的记录总有一个「事件发生了、记录还没写上」的窗口。
- **合并**：承认分不清，给两种情况规定同一个反应。

外化要付出写和运维的代价，合并要付出语义的代价。每一处选哪种，就是下面各节的取舍。

| 01 的项 | v3 | v4 |
| --- | --- | --- |
| N1 缺失是没创建还是丢了 | 外化：被删的 Pod 自己留在原地（finalizer）。没有证据的缺失合并成「创建」 | 外化：ServingGroup 的 `status` 里记「已建成」。建成之前的缺失合并成「创建」 |
| N2 终止中的 Pod 是谁删的 | 外化：带不带保护 finalizer。计划内的删除先摘再删 | 外化：删除之前先在 `status` 里写「清空中」或「失败」 |
| N3 残留还是已经开始 | 不再存在：证据只出现在已经被删的 Pod 上，删除不可撤销 | 不再存在：一个对象上的一次写 |
| N4 范围种类 | 外化：范围种类在 finalizer 的名字里，随删除冻结 | 组的范围是对象本身；实例的范围是账本里的一项 |
| N5 故障起点 | 不动，列为豁免 | 同左 |
| N6 在途的写 | 保留 v2 的逐对象叠加；去掉失败记录 | 组一级可以用整个 key 的屏障，见 [04](04-v4-servinggroup-cr.md) |
| N7 终止中的 surge 单元 | 补规则：标记从终止中的 Pod 上读 | 组一级没有 surge 标记 |
| N8 改 `updateMethod` | 见 [05](05-inplace-usage-isolation.md) | 同左 |

## 3. 「成员缺失」的路线

要回答的是同一个问题：**「这个范围丢过成员」这个事实放在哪里。**先看 API 对用户的承诺（走读，`pkg/apis/workload/v1alpha1/model_serving_types.go:127-136`、`servinggroup_types.go:117-125`）：`ServingGroupRecreate`、`RoleRecreate` 是「任何一个 Pod 被重建或任何容器重启，就重建全部 Pod」；grace 为 `-1` 时「被别人删除的 Pod 仍然按 `recoveryPolicy` 重建」。

### 3.1 候选

| 路线 | 证据是什么，谁写的 | 提交是否原子 | 留证据的窗口 | 每次删除多的写 | controller 不在时 | 主要代价 |
| --- | --- | --- | --- | --- | --- | --- |
| **A1** 改语义：缺失一律补建，整范围重建只由终态和重启故障触发 | 没有 | — | — | 0 | 结果与在场时相同 | 外部删除（驱逐、排空节点、抢占、手工删）只补一个，与上面两条 API 注释不一致 |
| **A2** 看得见的终止中的 Pod 当证据 | `deletionTimestamp`，删除者写的 | 是 | 终止期一过就没了；强制删除看不到 | 要区分自己的删除，仍然多一次写 | 离开超过终止期，证据消失 | 结果取决于时刻。模型：P2、P4 都违反 |
| **B** 受保护的 Pod 带 finalizer | 被删的 Pod 自己。**删除者的那一次 DELETE 就把证据写好了** | 是 | 没有窗口。例外是 finalizer 被人摘掉、绕过 API | 计划内删除每个 Pod 多 1 次 PATCH | 被删的 Pod 停在终止中，直到 controller 回来 | 运维：卡住的 Pod、卸载和回退的顺序、升级窗口 |
| **B 收窄** 只给范围多于一个 Pod 的加 | 同上 | 同上 | 同上 | 单 Pod 的范围是 0 | 单 Pod 的范围不受影响 | 同 B，只落在多 Pod 的范围上 |
| **C** 建成之后在成员 Pod 上写「已建成」 | 幸存成员上的注解 | 不是，n 个 Pod 各写一次 | 至少两个成员写上之前 | 范围比单元大时，每次计划内的成员变化都要改写幸存成员 | 回来之后认得 | 跨对象的一致性要靠协议。模型：建成窗口里 P2；范围比单元大时缩容被当成丢失，P4 |
| **D** ModelServing 注解里的账本，每个范围一项 | ModelServing 一个对象 | 是 | 成员建出来到记进账本之间 | 不按 Pod 计。计划内删除之前先改账本 | Pod 正常消失；回来之后账本里有、对象没有，认得 | 状态放在 metadata 里；`kubectl replace` 和整体替换式的同步工具会抹掉它；注解有大小上限；每轮多一次主资源的写 |
| **E** 账本放在 ConfigMap 里 | 另一个对象 | 是 | 同 D | 同 D | 同 D | 多一种要管生命周期和权限的对象。按组一个 ConfigMap 就是没有 schema 的 ServingGroup CR |
| **F** 用 PodGroup | — | — | — | — | — | 不成立：PodGroup 只在装了 CRD 并且用到 gang 时才有；按组一个，没有 Role 实例这一级；整组重建时它自己被删 |
| **H** worker 的 owner 指向同实例的 entry Pod | 结构本身，垃圾回收执行 | 是 | 没有 | 0 | entry 被删仍然级联 | 只解决一半：worker 被删还是分不清；组一级没有单一的 entry |

### 3.3 推荐

**v3 采用 B 收窄。**排序是 B 收窄、D、A1，其余不采用。

1. **B 是唯一「事件本身产生证据」的路线。**删除者的那一次 DELETE 同时写下了证据，不需要 controller 事后补一笔。所以它没有「建成之前」的窗口（C、D 有），也没有「第一个标记写上之前」的窗口（v2 的 O9）。每个 Pod 只带自己的事实，范围的状态全部是推导的，没有跨对象的一致性要维护。
2. **必须收窄。**默认策略是 `RoleRecreate`，没有 worker 的 Role 实例只有一个 Pod。范围只有一个 Pod 时，「整范围重建」和「补这一个」删掉和创建的是同一个 Pod，finalizer 没有任何语义上的作用。收窄之后，这些 Pod 一个写都不多，`kubectl delete pod` 的习惯不变。这种形态占多少没有数据；仓库的 16 个示例里有 13 个的范围多于一个 Pod，会带 finalizer。
3. **A1 不是被否决的路线，是 B 的降级形态。**没有 finalizer 的 Pod（存量的、范围只有一个 Pod 的、开关关掉时的全部 Pod）被删除，只补这一个，这就是 A1。所以每个 Pod 不论带不带 finalizer，反应都是确定的。开关关掉是紧急手段，那时范围策略下多 Pod 的范围比 v1、v2 都弱，见 03 的 9.2。
4. **B 的代价是运维上的。**它必须和下面四样一起交付，写在 [03](03-v3-state-machine.md) 的第 9 节：停止的定义；放行不属于自己的 Pod 的规则和 informer 的可见范围；不依赖 controller 的清理办法；分两个版本引入。

社区的情况（调研报告第 1 节）：

- 「创建时带 finalizer，自己删之前先摘，带着 finalizer 的删除算作失败」已经 GA 的先例是 Kubernetes Job 的 `batch.kubernetes.io/job-tracking`（[KEP-2307](https://github.com/kubernetes/enhancements/tree/master/keps/sig-apps/2307-job-tracking-without-lingering-pods)，1.26 stable）。它的孤儿队列、接管时补 finalizer、特性关掉时摘掉，和 v3 的规则一一对应。它是计数的场景，不是成组重建的场景。
- 成组的 workload controller 里没有已合入的同类做法。LeaderWorkerSet 和 RoleBasedGroup 都承认同一个缺口：[kubernetes-sigs/lws#1301](https://github.com/kubernetes-sigs/lws/issues/1301)（在途的方案是 finalizer，[#1319](https://github.com/kubernetes-sigs/lws/pull/1319)，没有合入），[sgl-project/rbg#562](https://github.com/sgl-project/rbg/issues/562)（在途的方向是 status 里的建成记录）。这两个方向正好对应 v3 和 v4。
- 用了 Pod finalizer 的项目都有 Pod 卡在终止中的事故记录：Job（kubernetes/kubernetes#108297、#121828）、Kueue（kubernetes-sigs/kueue#13830，带序号的同名 Pod 被没释放的 finalizer 挡住，StatefulSet 永远补不出来）、Argo Workflows（argoproj/argo-workflows#17480，默认关闭）。

### 3.4 D 为什么排在第二，什么时候应当排第一

D 和 v4 是同一个机制：范围一级的事实放在一个对象上，一次带 resourceVersion 的写就是提交。差别只是账本放在 ModelServing 的注解里，还是放在 `ServingGroup.status` 里。

D 相对 B 的好处是没有卡住的风险，回退时注解是惰性的。它的问题有三个。

- 它有建成之前的窗口：成员建出来到记进账本之间的丢失只补一个。B 没有。
- 计划内的每一次成员变化都要先改账本再动手，否则缩容会被当成丢失。这和 v2 的 M1 是同一类次序约束，只是从多个 Pod 变成了一个对象。
- 状态放在 metadata 里，会被整体替换式的工具抹掉。抹掉之后的安全默认是「没建成」，语义悄悄退化成只补。

「建成记录」在 fork 的生产分支上试过两种载体：ConfigMap（路线 E）和 Pod 注解（路线 C），最后都退掉了，只留在进程内存里（01 的 2.3）。退掉的原因没有记录在案，这里只当作一个提醒，不当作论据。

**如果 v4 确定要做，而且不远，D 应当排在 B 前面。**v3 用 finalizer 意味着两次迁移：v1 到 v3 给 Pod 加上，v3 到 v4 再全部摘掉，每一次都有升级窗口的风险。先做 D，账本以后原样搬进 `ServingGroup.status`。这一条要维护者裁定两件事：注解里的账本算不算违反「CRD 字段不增不删」的本意；v4 是不是确定的后续。本文按「v4 是否做还没有定」写，所以推荐 B 收窄。

### 3.5 没有采用的变体

| 变体 | 内容 | 为什么没有采用 |
| --- | --- | --- |
| 证据转移 | 看到持有的 Pod 之后，在同范围一个活着的成员上写一个注解，立刻放行被删的 Pod | 好处是被删的 Pod 只多停一轮，03 的 9.1「controller 在场时的等待」也随之消失。代价是证据有了两种形态，每次恢复多一次写，提交点从删除者的 DELETE 变回 controller 的 PATCH；接手证据的那个成员之后被缩掉或被人删掉时，证据要再转一次。没有模型证据。可以作为后续的优化单独评估 |
| 不收窄 | 范围策略下每个 Pod 都带 | 模型里没有发现它比收窄多保证什么；默认配置的所有 Pod 都承担运维代价 |
| 用 webhook 在准入时加 finalizer | LeaderWorkerSet 的在途方案这样做 | controller 自己创建 Pod，在创建请求里带上就行，不需要 webhook，也不依赖 webhook 可用 |

## 4. v3 的其他取舍

每一条写明：选了什么，没选什么，碰到哪个已批准的决定，是不是 DFA 必需的。

### 4.1 计划内的删除：先摘再删

选：缩容、回收 surge、滚动替换、`None` 下终态 Pod 的重建，都是先 PATCH 摘掉 finalizer，再 DELETE。PATCH 带计划时看到的 resourceVersion；DELETE 带 PATCH 返回的 resourceVersion。

没选：先 DELETE，再摘。模型里这个变体在没有任何丢失的缩容场景下出现 P4（232 个状态）：DELETE 之后、摘之前停下，副本数又改回去，这个 Pod 成了丢失的证据，整个范围被重建。

必需：是。「自己删的」和「别人删的」必须在对象上分得开（N2），而且区分必须在 DELETE 之前写好。

代价：每个受保护的 Pod 的计划内删除多一次 PATCH。两次写之间停下，Pod 是「活着、不带 finalizer」：还要删就接着删；不要删了就加回去，加回去之前这个 Pod 不受保护。

### 4.2 恢复的范围：已经开始的按原范围做完

选：保留 v2 的 D11 和 C4。范围种类放进 finalizer 的名字：`recover-role` 和 `recover-servinggroup` 两个。活着的 Pod 的 finalizer 跟着策略换名字；正在删除的对象不能加 finalizer，所以持有的 Pod 的名字换不了，范围种类在被删的那一刻冻结。

没选：范围取自最新的 `spec`（草稿里的 F9）。它少一条规则，但是：

- 它不是 DFA 必需的。两种做法都是快照的函数。
- 它的 `None` 一支让结果取决于停下的时刻：第二步删了一部分之后策略改成 `None`，留下几个成员取决于那一轮的 DELETE 发到第几个。不崩溃时一轮里的 DELETE 会发完，崩溃时才出现中间的结果（模型，3.2 的第二张表）。
- 它改掉四处已批准的行为：已经开始的恢复换了 leader 也按原范围做完；改成 `None` 之后仍然做完；`RoleRecreate` 改成 `ServingGroupRecreate` 时只做完原来的实例；反方向时整个组做完。

必需：不是，所以不改。

代价：策略在两种范围策略之间变化时，每个活着的受保护 Pod 一次 PATCH。策略变化之后、某个 Pod 的 finalizer 换名之前它被删了，按旧的范围恢复；换名是限量进行的，窗口到全部换完为止。v2 里两种范围的标记互斥（M7），新策略下的承诺要等旧的做完；v3 里两种名字的持有 Pod 可以并存，各算各的范围。

### 4.3 两步删除的第二步：等到「只差放行」

D15 规定先删故障的成员，范围里正在终止的 Pod 都消失之后再删其余的。带着 finalizer 的 Pod 不会消失，所以条件要改写。

选：范围里正在终止的 Pod 都「只差放行」或者已经消失时走第二步。只差放行指：有 `deletionTimestamp`；除了保护 finalizer 没有别的 finalizer；并且 `deletionGracePeriodSeconds` 为 0。

这个条件等价于「如果没有保护 finalizer，这个对象已经不在了」（推断，按 apiserver 和 kubelet 的源码）：

- kubelet 做完全部清理（包括卷卸载）之后发的最后一次 DELETE、强制删除、对没调度过的 Pod 和终态 Pod 的删除，都把 `deletionGracePeriodSeconds` 置 0。对象还有 finalizer 时它不被移除，停在这个值上。
- 节点失联时没有人发最后一次 DELETE，条件不成立，其余成员继续运行，直到有人强制删除或节点回来。这与 v2 相同。例外是 Pod 自己的 `terminationGracePeriodSeconds` 为 0：普通的删除也立刻得到 0，v2 里这样的对象同样立刻消失。
- Pod 上有别人的 finalizer 时条件不成立，其余成员继续运行。这与 v2 相同：v2 里这个 Pod 也不会消失。

没选：再加一个条件「或者 `phase` 是终态」。1.27 起 kubelet 在最后一次 DELETE 之前先把 `phase` 置成终态，但两者之间隔着卷卸载和 cgroup 清理。卷卸载卡住时，v2 里被删的 Pod 没有消失，其余成员继续运行；按 `phase` 判断会把它们删掉。旧于 1.27 的 kubelet 也不写终态。

没选：一步删完，不等。模型里这个变体只违反 P8（就是 D15 本身），不违反收敛和 P2。所以 D15 是行为上的选择，不是正确性的要求；v3 保留它是因为它已经批准。

必需：改写是必需的，结果与 v2 相同。

### 4.4 让路换成两条从快照得出的规则

v2 里 A9 排在两层的滚动之后，本轮被缩容、回收 surge、替换选中的单元整个跳过，这叫让路。它需要一份内存：上一轮对故障成员的 DELETE 确定失败时不让路。让路要处理的有两种成员。

- **被选中的单元里故障的成员。**v3：这个单元里活着的 Pod 都按计划内删除处理（先摘再删），故障的成员也一样，不提交。失败记录随之去掉。它原来挡的情形是「单元的删除一直失败，故障成员被永久让路」；v3 里故障成员就是由那次计划内删除来删的，没有另一条路可以让（推断）。
- **被选中的单元里被别人删掉的成员。**范围不比单元大时不需要规则：单元里活着的 Pod 被计划内删除之后，持有的 Pod 的范围里没有活着的 Pod 了，按正常的条件放行。范围比单元大只有一种情形：`ServingGroupRecreate` 下调小 `roles[].replicas`，要缩掉的 Role 实例里有一个 Pod 被别人删了。v2 规定这时不重建整个组。v3 的规则是：现存的实例多于副本数时先选出要缩掉的实例（没有活着的 Pod 的优先，其余按 A3 的次序），这一步不看恢复的状态；这些实例里的持有 Pod 不是证据；等实例里没有活着的 Pod 之后放行它。

第二条里「先选出要缩掉的实例」是为了打破循环：实例是不是在恢复中取决于持有的 Pod 算不算证据，而算不算又取决于实例是不是要缩掉。选择只用 `spec` 和成员状态，是快照的函数。按现存的实例数、让没有活 Pod 的实例优先，是为了让一个实例从被选中到 Pod 全部消失一直算要缩掉的。

放行排在实例里活着的 Pod 被删之后，是为了中途停下时证据还在：副本数又调回去时，持有的 Pod 回到期望位置上，范围照常恢复。放行要等这件事在模型里有一个一般的证据：一看到持有的 Pod 就放行的变体违反 P2（12 个终局）。那个场景没有缩容，不专门针对要缩掉的实例。

必需：是。那份失败记录是 01 里会改变计划的内存之一。

与 v2 的差别：丢失发生在缩容之前一轮以上时，v2 已经给整个组写了标记，会重建整个组；实例的 Pod 全部被别人删掉时，v2 不会选它来缩，也会重建整个组。v3 只看当时的对象，两种都不重建（03 第 8 节 L8）。

### 4.5 封闭：什么时候不创建

选：缺失的成员在两种情况下不创建。

1. 它在一个恢复中的范围里（范围按持有的 Pod 自己的 finalizer 算）。
2. 它所在的范围（按当前策略）里有本轮要提交的故障成员。

第 1 条保证新旧两批成员不会同时运行，对应 v2 的 M4。它成立的前提是放行的条件：期望位置上的持有 Pod 要等到它自己只差放行、范围里没有活着的 Pod、范围里期望位置上别的终止中 Pod 都是盖住这个范围的持有 Pod 才放行。所以范围里只要还有上一批的 Pod，范围就还在恢复中。例外是要缩掉的实例里的 Pod，它们不挡放行。第 2 条避免建出来立刻又删，对应 v2「承诺一个范围时撤掉本轮计划里落在这个范围内的创建」。

没选：范围策略下，范围里有任何成员在终止就不创建。它不需要上面的放行条件，但比 v2 宽：不带 finalizer 的 Pod 被删之后，同范围别的缺员要等它走完才补；它卡在失联的节点上时一直不补。

没选：范围里有活着的成员该带保护 finalizer 而没带时不创建。它能缩短 03 第 8 节 L1 的窗口，代价是接管期间范围里的补建和扩容都要等，PATCH 一直被拒绝时一直不补。

模型里去掉封闭的变体违反 P3（213 个状态），并且出现建了又删的循环。

必需：第 1 条是。第 2 条不是，与 v2 相同。

### 4.6 故障起点：保留，列为豁免

选：D9 不变。重启故障的 grace 从本 leader 第一次看到它故障起算，起点在内存里。

它是 J2 上界的豁免项：每换一次 leader 最多多等一个 grace，上界与重启次数有关。重启间隔一直短于 grace 时故障成员永远不删；这时别的功能也都不工作。

没选：起点取自 Pod。Pod 上能读到的只有 Ready 条件的 `lastTransitionTime`。真实的起点是「不 Ready」和「第一次计划外重启」里较晚的一个，后者 Pod 上没有。按 Ready 的时间算，一个加载模型很慢、中途重启过一次的 Pod 会立刻到期，grace 的含义从「容忍重启故障多久」变成了「启动期限」，在慢启动这个最常见的情形下反而缩短等待。

必需：不是。建议只做一件不改语义的事：在 `status` 的阻塞原因里写出从什么时候起算、还要等多久。

### 4.7 在途的写：保留逐对象的叠加

选：v2 的做法不变。本进程已经发出、缓存还没看到的写，按对象叠加到观察上。

没选：整个 ModelServing 的写后屏障（自己的写被缓存看到之前不再计划这个 ModelServing）。它更简单，但 04 的 4.1 已经否定过：一个单元上不被确认的写会挡住其他单元的故障恢复。v3 的队列 key 仍然是 ModelServing，这条理由仍然成立。

必需：不涉及。两种都只推迟。

### 4.8 上一任留下的终止中的 Pod

选：证据就是证据。带着保护 finalizer 的终止中的 Pod，不论是谁、什么时候删的，都是丢失；不带的都不是。

v2 的做法是「开始担任 leader 时已经在终止的，一律不算外部删除」，这正是 N2。v3 里不需要这条规则，也不需要那份集合。

必需：是。

### 4.9 Pod 全部在终止的临时单元

04 的待决项 O11：带 surge 标记的单元 Pod 全部在终止时，算正式单元还是临时单元，没有规定（01 的 N7）。

选：标记是 Pod 的注解，终止中的 Pod 仍然带着。单元带不带标记，按它现存的全部 Pod 判断，包括终止中的。

必需：是 J8 要求的补全。它是一个建议，要和 O11 一起裁定。

## 5. v4 的取舍

v4 的取舍在 [04](04-v4-servinggroup-cr.md) 里展开，这里只列条目，方便和 v3 对照。

| 取舍 | 推荐 | 没选的 | 碰到的决定 |
| --- | --- | --- | --- |
| 粒度 | 只有 ServingGroup 是 CR；Role 实例保留序号，状态记在组的 `status` 里 | Role 实例也去序号；Role 实例也做 CR | 无 |
| 组怎样被删 | 前台级联。组失败之后，等故障的成员被删掉并且消失再删组 | 组自己的 finalizer；后台级联 | D15 在 `ServingGroupRecreate` 下靠两个 controller 的次序保留 |
| 组一级的 partition | 按数量：至多保留 P 个基线版本的组 | 保留序号只为了 partition | **改变**：不能再指定哪几个组留在旧版本；基线版本的组少于 P 时，扩容和重建出来的是旧版本 |
| 多建 | 名字由 controller 生成，屏障带期限，多了按数量缩回 | 创建之前在 `ModelServing.status` 里预留名字 | 不变量 I1 从每一步成立变成最终成立 |
| 建成之前的丢失 | 只补 | 再加 Pod finalizer | 比 v3 弱，见 04 |
| LWS 兼容路径 | v4 不覆盖，或者它的组保留序号名字 | 给随机名字的组再分配一个整数 | 待定 |

## 6. 模型说明了什么，没有说明什么

模型在任务目录的 `model/` 下，纯 Python 标准库，用 `uv run` 执行。它穷举 controller、kubelet 和有限次扰动的全部交错。

说明了的：

- v3 的规则在 3.2 的场景里没有违反任何一条性质，四类场景下有无崩溃的终局集合相同。
- 每去掉一条规则，都有一条对应的性质被违反（4.1、4.4、4.5 里引的数字，另有「故障成员带的名字不对时直接删」违反 P2）。「一步删完」只违反 D15 本身。这说明规则是需要的。
- 别人的 finalizer、失联的节点、存量 Pod 的升级、finalizer 被人摘掉、范围大小在 1 和多之间变化，这些场景下都收敛，没有留下持有的 Pod。恢复的删除在计划时都满足两个条件：范围里有期望位置上的持有 Pod；范围里没有还在终止而不是只差放行的 Pod。这两个条件用的是模型内核里一份只看 Pod 字段的参考定义，不是被检查的设计自己的函数。
- 不受保护的 Pod 被删只补一个，记为说明，不是违反。

没有说明的：

- 规模。跑过的形状是 1×2×2、2×1×2、1×2×1（组数 × 每组的实例数 × 每个实例的 Pod 数），最多 4 个 Pod；至多两次扰动加一到两次 `spec` 变更。
- v3 在模型里没有内存，所以「内存不改变计划」对它是构造出来的，不是验证出来的。在途的写和故障起点不在模型里。
- 写落地时的情形。性质在计划时检查；计划之后别的成员又被删、`spec` 又变了的情形记为说明（03 第 8 节 L6）。
- 没有滚动：替换、surge、partition、两个额度都不在模型里。v3 的滚动规则沿用 v2，由 005 的参考模型覆盖；两者的衔接（4.4）是推演，没有模型证据。
- 没有按落后的快照计划，没有第二个 controller 实例，没有时间和 grace。J5、J6 的结论是推演。
- 模型里「不再需要的位置」由序号唯一决定；实际的缩容先选未就绪的。模型里没有外来的 Pod。
- v4 的模型没有覆盖缓存新旧不一、创建不幂等和按数量的 partition，见 04。
